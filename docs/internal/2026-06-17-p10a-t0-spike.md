## S1 — Does GPUI 0.2.2 deliver double-clicked files to the app?

### Verdict: PASS

GPUI 0.2.2 exposes `App::on_open_urls(|urls: Vec<String>|)` on both macOS and Linux. On macOS it is backed by an `NSApplicationDelegate application:openURLs:` implementation. macOS delivers double-clicked files as `file://` URLs through that delegate method — **not** via `std::env::args()` — so the existing `cli_paths` argv path in `main.rs` does NOT receive macOS double-click events.

### Evidence

Search command:
```
find ~/.cargo -path "*gpui-0.2.2*" -name "*.rs" | xargs grep -lniE "open_urls|openurls|on_open|reopen|OpenUrls"
```

Files hit: `src/app.rs`, `src/platform.rs`, `src/platform/mac/platform.rs`, `src/platform/linux/platform.rs`, `src/platform/test/platform.rs`, `src/platform/windows/platform.rs`

**`src/app.rs` lines 188–194:**
```rust
/// Register a handler to be invoked when the platform instructs the application
/// to open one or more URLs.
pub fn on_open_urls<F>(&self, mut callback: F) -> &Self
where
    F: 'static + FnMut(Vec<String>),
{
    self.0.borrow().platform.on_open_urls(Box::new(callback));
    self
}
```

```rust

```

**`src/platform/mac/platform.rs` lines 706–707 (trait impl):**

**`src/platform/mac/platform.rs` lines 1447–1467 (extern C handler):**
```rust
extern "C" fn open_urls(this: &mut Object, _: Sel, _: id, urls: id) {
    let urls = unsafe {
        (0..urls.count())
            .filter_map(|i| {
                let url = urls.objectAtIndex(i);
                match CStr::from_ptr(url.absoluteString().UTF8String() as *mut c_char).to_str() {
                    Ok(string) => Some(string.to_string()),
                    Err(err) => { log::error!("error converting path to string: {}", err); None }
                }
            })
            .collect::<Vec<_>>()
    };
    // ... invokes the registered callback
}
```

**`src/platform/linux/platform.rs` lines 287–288:**
```rust
fn on_open_urls(&self, callback: Box<dyn FnMut(Vec<String>)>) {
    self.with_common(|common| common.callbacks.open_urls = Some(callback));
}
```

### Decision for T6/T10

**T6** must:
1. Set `CFBundleDocumentTypes` in `Info.plist` (so Finder shows dat0 as opener for `.dat0`).
2. Register `cx.on_open_urls(|urls| { ... })` inside `run_app` (inside `Application::new().run(|cx| { ... })`). The callback receives `file:///absolute/path.dat0` strings; strip the `file://` prefix (or use `url::Url::parse` → `to_file_path()`) to obtain a `PathBuf`, then call the same `handle_drop(paths, Arc::clone(&session))` path the argv cold-start uses (see `window.rs` lines 1629–1645).
3. On Linux, set `.desktop` file `MimeType=application/x-dat0;` and register `x-dat0` via `shared-mime-info`. The `on_open_urls` callback fires via XDG on Wayland/X11 (backed by `ashpd` / `xdg-open`). This is the spec's hard Linux exit gate.

**T10** conditional deferral: NOT needed. The hook exists at this pin; macOS double-click is fully deliverable in v1.0. No objc2 shim required.

## S2 — Universal binary under hardened runtime

### Verdict: PASS — entitlement set is EMPTY

A lipo'd `aarch64 + x86_64` universal binary of the real app builds cleanly, signs under the hardened runtime (ad-hoc), and verifies strict with no entitlements.

### Commands and output

**Step 1: add x86_64 target (was not installed)**
```
rustup target add x86_64-apple-darwin
```

**Step 2: build arm64 release**
```
cargo build -p dat0-app --release --target aarch64-apple-darwin
```
Output: `Finished 'release' profile [optimized] target(s) in 5m 21s`

**Step 3: build x86_64 release (cross-compile from Apple Silicon)**
```
cargo build -p dat0-app --release --target x86_64-apple-darwin
```
Output: `Finished 'release' profile [optimized] target(s) in 4m 15s`

Note: the binary name is `dat0` (not `dat0-app`) in both release dirs.

**Step 4: lipo**
```
lipo -create \
  target/aarch64-apple-darwin/release/dat0 \
  target/x86_64-apple-darwin/release/dat0 \
  -output /tmp/dat0-universal
```
No errors.

Key flags: `0x10002 = adhoc | runtime` — hardened runtime enabled, no JIT, no unsigned memory.

### Decision for T6/T7

**Entitlement set: EMPTY.** DuckDB does not JIT; Metal static libs don't require `com.apple.security.cs.allow-jit` or `com.apple.security.cs.allow-unsigned-executable-memory`. The hardened runtime accepts the binary without any entitlements.

T6 entitlements file: an empty `<dict/>` (or omit entirely — `codesign` with `--options runtime --sign <identity>` without `--entitlements` is sufficient).

T7 (notarization) should use the same empty entitlement set. `xcrun notarytool submit` of a DMG containing this binary will not be blocked by entitlement issues.

Note for CI/T7: the ad-hoc sign (`--sign -`) used here is for local verification only. In the actual release pipeline, replace `-` with the Apple Developer ID certificate identity (e.g. `"Developer ID Application: ..."`) and submit to notarytool.
