## macOS

### What was verified EMPIRICALLY on this host (darwin arm64)

A minimal stand-in `.app` bundle was constructed in `/tmp/dat0-spike-t0/`:

```
dat0.app/
  Contents/
    MacOS/dat0     # executable shell script running `exec sleep 9999`
    Info.plist     # minimal CFBundleIdentifier/CFBundleExecutable
```

Four checks were run:

#### Check (a): move-aside → move-in works on a user-writable install

```bash
mv "$INSTALL/dat0.app" "$INSTALL/dat0.app.old"   # exit 0
mv "$V2/dat0.app" "$INSTALL/dat0.app"            # exit 0
```

Both `mv` calls (which use `rename(2)` on the same filesystem) returned 0. The v2 bundle appeared at the install path; v1 remained intact at `.old`. On the same filesystem, `std::fs::rename` is an atomic directory rename — no partial state is visible. **PASS.**

#### Check (b): running process survives bundle directory rename (critical mmap question)

```
Background PID: 68724
BEFORE rename: process 68724 is ALIVE
[mv dat0.app → dat0.app.old, exit 0]
AFTER rename:  process 68724 is ALIVE (bundle gone)
[mv v2 → dat0.app, exit 0]
AFTER move-in: process 68724 is ALIVE (v1 still running from .old)
```

The running process whose executable lives inside the bundle survived both the move-aside and the move-in without interruption. This is expected on macOS/HFS+/APFS: `rename(2)` on a directory changes only the directory entry; all existing open file descriptors, mmap'd pages, and page-cache references keep pointing to the original inode tree. The OS does NOT invalidate mmap'd executable pages when the containing directory is renamed. **PASS.**

#### Check (c): rollback mechanics

```bash
mv "$INSTALL/dat0.app" "/tmp/failed-update.app"
mv "$INSTALL/dat0.app.old" "$INSTALL/dat0.app"   # exit 0
```

v1 was restored at the install path. The rollback sequence is the exact inverse of the swap and works reliably. **PASS.**

#### Check (d): spctl on unsigned stand-in (illustrates the local testing limit)

```
$ spctl --assess --type execute -vvv /tmp/.../dat0.app
/tmp/dat0-spike-t0/install/dat0.app: rejected
source=no usable signature
Exit code: 3
```

**Expected-fail because unsigned, NOT because moved.** This output demonstrates why `spctl` cannot answer the notarization-survival question locally: any locally-built `.app` lacks a Developer ID signature and a Gatekeeper-stapled ticket, so `spctl` will always reject it regardless of path. The question below is answered by reasoning.

### Notarization survival — REASONED verdict

Notarization produces two artifacts stapled into the bundle itself:
1. `Contents/_CodeSignature/CodeResources` — the code signature covering all bundle contents
2. A Gatekeeper-stapled ticket embedded via `xcrun stapler staple` (stored in the bundle's extended attributes on the bundle directory (via `xcrun stapler staple`) — all of which are preserved by `fs::rename`)

When `std::fs::rename` moves the bundle directory, it moves the entire directory tree **intact** — all bytes, all extended attributes, all inodes are carried over; no re-signing or re-stapling occurs. Gatekeeper's assessment is content-and-staple-based and **path-independent**: it reads the signature from `_CodeSignature/CodeResources` and the stapled ticket from the bundle, then validates both against Apple's OCSP/notarization servers. The path on disk does not enter this computation.

Therefore: a notarized bundle moved via `fs::rename` remains fully notarized. **Verdict: PASS by design.** To be confirmed empirically in the clean-VM UAT (T9) by running `spctl --assess --type execute -vvv` on the CI-notarized DMG contents after extracting and renaming.

### Exact T4 sequence (macOS)

```rust
// 1. Derive install_root from current_exe()
//    current_exe() → …/dat0.app/Contents/MacOS/dat0
//    walk up 3 levels to get …/dat0.app
let exe = std::env::current_exe()?;
let install_root: PathBuf = exe
    .ancestors()
    .nth(3)                    // MacOS/ → Contents/ → dat0.app/
    .ok_or(anyhow!("cannot find .app bundle root"))?
    .to_path_buf();

// 2. Extract downloaded .app.tar.gz to a temp dir on the same filesystem
//    (must be same-filesystem as install_root for rename(2) to be atomic)
let tmp_extract = install_root.with_extension("app.new");
//    NOTE: the .app.tar.gz is produced by T7 as `tar -czf … -C target/macos dat0.app`,
//    so its root entry is `dat0.app/` → extracting into tmp_extract yields tmp_extract/dat0.app.
//    tar -C requires the dir to exist first:
std::fs::create_dir_all(&tmp_extract)?;
std::process::Command::new("tar")
    .args(["-xzf", &archive_path, "-C", &tmp_extract])
    .status()?;
//    (pseudo-code: PathBuf + &str cannot share one array literal — T4 should use chained .arg() calls)
let new_bundle = tmp_extract.join("dat0.app");

// 3. Move-aside current bundle
let backup = install_root.with_extension("app.old");
std::fs::rename(&install_root, &backup)?;

// 4. Move-in new bundle (atomic on same filesystem)
if let Err(e) = std::fs::rename(&new_bundle, &install_root) {
    // Rollback: restore the old bundle
    let _ = std::fs::rename(&backup, &install_root);
    return Err(e.into());
}

// 5. Clean up backup (best-effort — leave it on failure)
let _ = std::fs::remove_dir_all(&backup);

// 6. Relaunch via `open` — this is the macOS mechanism for launching a .app
//    The current process exits immediately after spawning.
std::process::Command::new("open")
    .arg(&install_root)
    .spawn()?;
std::process::exit(0);
```

**Why `open` not `Command::exec`?** The macOS `open` command launches the `.app` bundle through Launch Services, which respects the bundle's `CFBundleExecutable`, applies sandbox/entitlements correctly, and handles the case where an existing instance needs to be brought forward. Direct `exec` into the binary path bypasses Launch Services and can mis-behave with quarantine/Gatekeeper on first post-update launch.

**Same-filesystem requirement:** The temp extraction dir MUST be on the same filesystem as the install root so that `rename(2)` is atomic. Use `install_root.parent()` or a temp dir derived from it (e.g., `install_root.with_extension("app.new")`), NOT `std::env::temp_dir()` which may be a different volume (e.g., `/private/var/folders/…` on a separate APFS volume).

## Linux

### NOT runnable on this host — REASONED verdict

This host is darwin arm64. There is no AppImage runtime, no FUSE, and no Linux kernel. The Linux verdict is derived from known AppImage/FUSE semantics.

### AppImage/FUSE mechanics — REASONED

A running AppImage is:
1. Treated by the kernel as an ELF executable with a self-contained SquashFS payload.
2. At launch, the AppImage runtime (embedded offset 0) calls `FUSE` to mount the SquashFS at a temp mountpoint (e.g., `/tmp/.mount_dat0XXXXXX`).
3. The FUSE mount holds an **open file descriptor** (via `open()` + `mmap()`) referencing the **original inode** of the AppImage file.

When you write a new AppImage file to disk:
- **`cp` over the file** (`cp new.AppImage target.AppImage`): truncates and rewrites the **same inode** — this can corrupt the FUSE mount of a running instance because the mmap'd pages reference the same inode that is being mutated.
- **`rename`-of-temp-over-target** (`rename("new.AppImage.tmp", "target.AppImage")`): creates a brand-new inode at the target path; the old inode (referenced by the running FUSE mount) remains alive, intact, and accessible until the process exits and the last fd/mmap is closed. The on-disk path now points to the new inode.

**Critical mandatory constraint for T4:** use `std::fs::rename` of a fully-downloaded temp file over the target path. **Never use in-place `cp`/`write` over the target.**

The `APPIMAGE` environment variable is set by the AppImage runtime to the **original path** from which the AppImage was launched (e.g., `/home/user/Applications/dat0.AppImage`). This is the path T4 uses as the relaunch target after the rename.

After `rename`, relaunching via `std::os::unix::process::CommandExt::exec` replaces the current process image with the new AppImage. The new AppImage's embedded runtime mounts the new inode's SquashFS. The old inode (old AppImage) is then released when the process exits.

### Exact T4 sequence (Linux)

```rust
use std::os::unix::fs::PermissionsExt;
use std::os::unix::process::CommandExt;

// 1. Derive install path
//    Prefer APPIMAGE env var (set by AppImage runtime); fall back to current_exe()
let install_path: PathBuf = std::env::var("APPIMAGE")
    .map(PathBuf::from)
    .unwrap_or_else(|_| std::env::current_exe().expect("current_exe"));

// 2. Download new AppImage to a temp file on the SAME filesystem as install_path
//    (use install_path.parent() to ensure same-filesystem for atomic rename)
let tmp_path = install_path.with_extension("AppImage.new");
// … write downloaded bytes to tmp_path …

// 3. chmod +x the temp file
std::fs::set_permissions(&tmp_path, std::fs::Permissions::from_mode(0o755))?;

// 4. Keep a .old for rollback (optional but recommended)
let backup_path = install_path.with_extension("AppImage.old");
let _ = std::fs::rename(&install_path, &backup_path);

// 5. Atomic rename: new inode → target path
//    This is the MANDATORY step. Do NOT use std::fs::copy or write-in-place.
if let Err(e) = std::fs::rename(&tmp_path, &install_path) {
    // Rollback
    // Only roll back if the move-aside in step 4 actually produced a backup —
    // otherwise a failed move-aside + failed rename would leave NO AppImage at the target.
    if backup_path.exists() {
        let _ = std::fs::rename(&backup_path, &install_path);
    }
    return Err(e.into());
}

// 6. Clean up old backup (best-effort)
let _ = std::fs::remove_file(&backup_path);

// 7. Relaunch via exec — replaces current process image
//    exec does not return on success
let err = std::process::Command::new(&install_path)
    .exec();  // CommandExt::exec — replaces the process image
// If we reach here, exec failed
Err(err.into())
```

**Why `exec` not `spawn`?** On Linux, `exec` replaces the current process (same PID), which is cleaner for a self-updater: there is no window where both old and new processes are running simultaneously. The old AppImage's FUSE mount is released when the old process image is replaced. On macOS, `exec` into the raw binary bypasses Launch Services, so `open` is preferred instead.
