# dat0 P10c — Crash Reporting UAT Checklist

> **Date:** 2026-06-24
> **Phase:** P10c (crash reporting e2e + D-029 settings hardening)
> **Tester:** perform on a **signed release build** compiled with the REAL
> `DAT0_GLITCHTIP_DSN_PUBLIC` DSN. A dev build using the `"invalid"` stub DSN
> will not transmit events and will not exercise the end-to-end path.
> **Notation.** `[ ]` = not yet tested; `[x]` = PASS; `[!]` = FAIL (note details)

---

## Prerequisites

- Build from branch `p10c-crash-reporting` (or post-merge `main` once P10c is merged),
  compiled with the real GlitchTip DSN:
  ```bash
  DAT0_GLITCHTIP_DSN_PUBLIC="<real-dsn>" cargo build -p dat0-app --release --bin dat0
  ```
- Confirm `.cargo/config.toml` has the `"invalid"` stub for `DAT0_GLITCHTIP_DSN_PUBLIC`;
  override it only via the shell env var above or a local `config.toml` override — do
  **not** commit the real DSN to source control.
- Have the GlitchTip Issues page open in a browser tab, filtered to the dat0 project,
  ready to receive events (`environment:production` filter).
- Close any prior dat0 instances before each sub-section so the sentinel state is clean.
- Each sub-section that checks for the absence of a sentinel (`last-crash.json`,
  `running.marker`) should confirm with:
  ```bash
  # macOS
  ls ~/Library/Application\ Support/dat0/
  # Linux
  ls ~/.config/dat0/
  ```

## Known caveats (read before testing)

1. **GlitchTip API path**: the `crash-e2e.yml` CI gate uses
   `/api/0/projects/<slug>/issues/`. Confirm the correct path for the self-hosted
   instance during §4 smoke test; update the workflow comment if the path differs.

2. **Crash dialog on clean exit**: a clean exit (no crash) must leave no
   `last-crash.json`. The relaunch dialog appears only when the sentinel exists AND
   opt-in is enabled. If the dialog appears on a clean launch, the sentinel was not
   deleted on normal exit — that is a FAIL.

3. **Redaction scope**: the redactor strips home-directory prefixes from paths
   (`/Users/<name>/`, `/home/<name>/`). Schema names, query SQL, and column values
   are never included in the submitted payload (they are scrubbed before staging in
   `last-crash.json`). The PII check in §1.6 and §4 covers path redaction only;
   the absence of SQL/schema content is verified structurally by the P10c T3 test
   suite.

## 1. Opt-in crash submission — full round-trip

> Verifies: sentinel written on crash, relaunch dialog shown, note submitted,
> event arrives in GlitchTip with redacted paths, sentinel cleaned up.

### 1.1 Enable crash submission

- [ ] **1.1** Launch dat0. Open **View → Settings…** → **Telemetry**.
      Confirm the crash-submission toggle is currently **OFF** (default).
- [ ] **1.2** Turn the toggle **ON**. Close the Settings window.
      **Pass criterion:** toggle persists — relaunch dat0, open Settings → Telemetry,
      confirm toggle is still ON.

### 1.2 Trigger a panic

- [ ] **1.3** With the toggle ON, trigger a panic using the hidden debug action.
      The exact mechanism depends on the P10c implementation (e.g., a hidden menu item
      under Help, or a specific key chord documented in the T6 wiring note). Confirm
      dat0 **crashes** (process exits).
      **Pass criterion:** the process exits non-zero; no hang.

### 1.3 Confirm the relaunch dialog

- [ ] **1.4** Relaunch dat0 (`./target/release/dat0` or double-click the app bundle).
      Confirm a **crash-report dialog** appears on first launch after the crash.
      The dialog must show:
      - A message indicating dat0 crashed.
      - A free-form text area for the user to add a note.
      - A **Send** button and a **Dismiss** (or Don't Send) button.
      **Pass criterion:** dialog appears; no additional crash on relaunch.

### 1.4 Add a note and send

- [ ] **1.5** In the note field, enter a test string (e.g. `UAT P10c crash test`).
      Click **Send**.
      **Pass criterion:** dialog closes without crash; dat0 continues to the Home screen.

### 1.5 Verify arrival in GlitchTip

- [ ] **1.6** Wait ~15 seconds for ingestion. In the GlitchTip Issues list, confirm
      a new issue appeared corresponding to the crash event. Confirm:
      - The issue title reflects the panic message (not the user note — the note
        appears in the issue detail, not the title).
      - The issue detail includes the user note `UAT P10c crash test`.
      - The dat0 version, OS, and architecture are shown in the issue metadata.
      **Pass criterion:** event visible in GlitchTip with note and metadata.

### 1.6 PII redaction check

- [ ] **1.7** In the GlitchTip issue detail, inspect all path-like fields
      (`filepath`, `abs_path`, `module`, stack frames). Confirm:
      - No field contains `/Users/<your-username>/` (macOS) or `/home/<your-username>/`
        (Linux).
      - No field contains any query SQL, table name, schema name, or column values.
      **Pass criterion:** zero un-redacted home-directory paths; no SQL/schema content.

### 1.7 Sentinel cleaned up

- [ ] **1.8** After a successful Send, confirm `last-crash.json` no longer exists
      in the dat0 data directory.
      **Pass criterion:** no `last-crash.json` present after submission.

## 2. Help → Report a Bug

> Verifies: the Report-a-Bug flow sends a manual event with `report-a-bug` tag,
> independent of any crash sentinel.

- [ ] **2.1** Ensure dat0 is running cleanly (no prior crash sentinel). Open the
      **Help** menu. Confirm a **"Report a Bug…"** item is present.
- [ ] **2.2** Click **"Report a Bug…"**. Confirm a report modal opens with a text
      area for describing the bug. The modal must show **Send** and **Cancel** buttons.
      **Pass criterion:** modal opens without crash.
- [ ] **2.3** Enter a test description (e.g. `UAT P10c manual bug report`). Click
      **Send**.
      **Pass criterion:** modal closes; dat0 continues without crash.
- [ ] **2.4** Wait ~15 seconds. In GlitchTip, confirm a new event arrived with:
      - Message type (not exception), tagged or titled `report-a-bug` or similar
        (exact title determined by T7/T8 implementation — confirm it is distinct
        from the crash event).
      - The description text `UAT P10c manual bug report` visible in the detail.
      **Pass criterion:** event visible in GlitchTip with correct message and text.
- [ ] **2.5** Confirm no `last-crash.json` was created by this flow (Report-a-Bug
      must not touch the crash sentinel).
      **Pass criterion:** no `last-crash.json` after Report-a-Bug.

## 3. Opt-out — privacy-critical path

> Verifies: with crash submission OFF, a crash produces NO dialog on relaunch
> and NO submission to GlitchTip. This is the hardest privacy guarantee.

- [ ] **3.1** Open **View → Settings…** → **Telemetry**. Turn the toggle **OFF**.
      Close Settings. Quit dat0 cleanly.
      **Pass criterion:** toggle is OFF and persists across relaunch.
- [ ] **3.2** Trigger a crash (same mechanism as §1.2).
      **Pass criterion:** dat0 exits (crashes).
- [ ] **3.3** Relaunch dat0. Confirm:
      - **No crash-report dialog appears.** dat0 opens normally to the Home screen.
      - No event arrives in GlitchTip within 30 seconds (monitor the Issues list
        during the relaunch).
      **Pass criterion:** no dialog, no GlitchTip event. This is FAIL if a dialog
      appears or an event is visible.
- [ ] **3.4** Confirm `last-crash.json` does NOT exist in the dat0 data directory
      after the relaunch (the sentinel must have been discarded, not staged).
      **Pass criterion:** no `last-crash.json` present.
- [ ] **3.5** (Belt-and-suspenders) Confirm `running.marker` does NOT persist after
      a clean exit (subsequent launch following step 3.3).
      **Pass criterion:** no `running.marker` after a clean exit.

## 4. `dat0 __telemetry-test` smoke

> Verifies: the hidden CLI subcommand sends a synthetic event without triggering
> a real panic or leaving a crash sentinel.

- [ ] **4.1** Run the smoke command from the terminal:
      ```bash
      ./target/release/dat0 __telemetry-test
      ```
      Confirm the process exits **0** promptly.
      **Pass criterion:** exit code 0; no crash.
- [ ] **4.2** Wait ~15 seconds. In GlitchTip, confirm a new event with the title
      `"dat0 telemetry e2e"` appeared.
      **Pass criterion:** event visible in GlitchTip.
- [ ] **4.3** Inspect the event in GlitchTip. Confirm no un-redacted home-directory
      paths are present (same redaction check as §1.6).
      **Pass criterion:** no `/Users/<name>/` or `/home/<name>/` in any field.
- [ ] **4.4** Confirm no `last-crash.json` was created by `__telemetry-test`.
      **Pass criterion:** no sentinel on disk after the smoke command.
- [ ] **4.5** (GlitchTip API path validation) Note the URL used by the CI gate:
      `/api/0/projects/${GLITCHTIP_PROJECT_SLUG}/issues/`. Confirm this path is
      valid on the self-hosted instance by navigating to it in a browser with the
      API token. If the correct path differs (e.g. `/api/0/organizations/<org>/issues/`),
      update the comment in `.github/workflows/crash-e2e.yml`.
      **Pass criterion:** the documented API path returns 200 and lists the smoke event.

## 5. Clean-exit sentinel hygiene

> Verifies: a normal (non-crash) exit leaves no sentinel files that could trigger
> a spurious dialog on the next launch.

- [ ] **5.1** Launch dat0 (no prior crash). Open a workspace or stay on the Home
      screen. Quit dat0 cleanly (File → Quit, or Cmd-Q / Ctrl-Q).
      **Pass criterion:** dat0 exits normally.
- [ ] **5.2** Inspect the dat0 data directory:
      ```bash
      # macOS
      ls ~/Library/Application\ Support/dat0/
      # Linux
      ls ~/.config/dat0/
      ```
      Confirm:
      - No `last-crash.json` is present.
      - No `running.marker` is present.
      **Pass criterion:** neither file exists after a clean exit.
- [ ] **5.3** Relaunch dat0. Confirm no crash-report dialog appears.
      **Pass criterion:** clean launch, no dialog.
