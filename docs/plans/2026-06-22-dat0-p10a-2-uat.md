# dat0 P10a-2 Auto-Update — Clean-VM UAT Checklist

> **Purpose.** Manual acceptance tests for the P10a-2 in-app auto-updater
> (unified Rust updater: minisign-signed `latest.json` + one-click Install &
> Restart + cross-platform self-swap). These tests require a real signed and
> notarized release (macOS) or signed AppImage (Linux) and cannot be run
> headless.
>
> **Pre-condition.** Before running any of these scenarios, complete the
> production-key provisioning steps in `docs/security-runbook.md`
> § "minisign Update-Signing Key — Current state (dry-run blocker)":
> generate the production passwordless key, set `MINISIGN_SECRET_KEY`, and
> replace the embedded pubkey in `crates/dat0-app/assets/minisign-public-key.txt`.
> Then run a `workflow_dispatch` dry-run to confirm signing works end-to-end.
>
> **Notation.** ✅ = pass, ❌ = fail, ⚠️ = partial/notes.

---

## 1. macOS Update Round-Trip (clean VM)

> Install an older signed + notarized release. Point the updater at a newer
> signed release (via a local or staging `latest.json`). Confirm the one-click
> flow downloads, verifies, swaps, and relaunches.

- [ ] **1.1** Install the older release DMG on a clean macOS VM (no previous
      dat0 installation). Confirm Gatekeeper clears it:
      ```bash
      spctl --assess --type execute -vvv /Applications/dat0.app
      # expected: source=Notarized Developer ID
      ```
- [ ] **1.2** Launch dat0. Navigate to **Help → Check for Updates** (or wait
      for the launch-time check to fire). Confirm the "checking…" UI feedback
      appears.
- [ ] **1.3** When the update prompt appears, click **"Install & Restart"**.
      Confirm dat0 downloads `dat0.app.tar.gz` (progress visible or logged).
- [ ] **1.4** Confirm the minisign signature on `latest.json` is verified before
      download proceeds. (Test failure path separately — see §6.)
- [ ] **1.5** Confirm the SHA-256 of `dat0.app.tar.gz` matches the manifest
      entry before the swap is applied.
- [ ] **1.6** Confirm the `.app` bundle is swapped in place via `fs::rename`
      (no UAC prompt, no Finder copy dialog — swap is silent).
- [ ] **1.7** Confirm dat0 relaunches automatically into the new version (the
      GPUI window appears — headless cannot verify this; confirm manually).
- [ ] **1.8** After relaunch, confirm the About box shows the new version number.
- [ ] **1.9** Run Gatekeeper on the moved bundle to confirm notarization survives
      the rename:
      ```bash
      spctl --assess --type execute -vvv /Applications/dat0.app
      # expected: source=Notarized Developer ID  (PASS — notarization is
      # stapled to the .app, not to the install path; rename is safe)
      ```
      This is the T0 spike's reasoned PASS, empirically confirmed here.

## 2. Linux Update Round-Trip (clean VM)

> Same one-click round-trip with a real `.AppImage`.

- [ ] **2.1** Install the older signed AppImage on a clean Linux VM (Ubuntu or
      equivalent). Verify the GPG `.sig`:
      ```bash
      gpg --verify dat0.AppImage.sig dat0.AppImage
      ```
- [ ] **2.2** Launch dat0 via the AppImage (FUSE mount active). Navigate to
      **Help → Check for Updates**. Confirm the "checking…" feedback appears.
- [ ] **2.3** When the update prompt appears, click **"Install & Restart"**.
      Confirm the new `.AppImage` is downloaded and SHA-256 verified.
- [ ] **2.4** Confirm the `rename`-over-target swaps the `.AppImage` file.
      Because the AppImage is FUSE-mounted by the running process, the old inode
      remains held; `rename` replaces the directory entry but the running mount
      survives until the process exits. Confirm no filesystem error is surfaced.
- [ ] **2.5** Confirm dat0 execs the new `.AppImage` (relaunches into the new
      version). The GPUI window must appear in the relaunched process — confirm
      manually; headless cannot verify.
- [ ] **2.6** After relaunch, confirm the About box shows the new version number.

---

## 3. Not-Writable Fallback

> When dat0 is installed in a root-owned location, the updater must fall back
> to the nudge (open the Releases URL) rather than attempting the swap.

- [ ] **3.1** Install dat0 in `/Applications` (root-owned, not user-writable):
      ```bash
      sudo cp -r dat0.app /Applications/dat0.app
      sudo chown -R root:wheel /Applications/dat0.app
      ```
- [ ] **3.2** Launch dat0 from `/Applications/dat0.app`. Navigate to
      **Help → Check for Updates** (or wait for launch-time check).
- [ ] **3.3** When a new version is available, confirm dat0 does **NOT** attempt
      the swap. Instead it opens the GitHub Releases page in the browser (the
      P10a nudge fallback).
- [ ] **3.4** Confirm no error dialog or crash occurs.

---

## 4. Settings Opt-Out

> Setting `update_auto_check = false` must suppress the launch-time check.

- [ ] **4.1** Open **Settings** and disable **"Check for updates automatically"**
      (or set `update_auto_check = false` in `~/.dat0/settings.toml` directly).
- [ ] **4.2** Fully quit dat0 and relaunch.
- [ ] **4.3** Confirm no "checking…" UI or update prompt appears on launch (no
      network request to `latest.json` should fire).
- [ ] **4.4** Confirm **Help → Check for Updates** still works manually while
      the auto-check is disabled.

---

## 5. Manual Menu Action

> **Help → Check for Updates** must work end-to-end: show feedback, then the
> prompt / "up to date" / error state.

- [ ] **5.1** Launch dat0 with the current version already being the latest.
      Click **Help → Check for Updates**. Confirm an "up to date" message is
      shown (no crash, no empty state).
- [ ] **5.2** Point dat0 at a newer release. Click **Help → Check for Updates**.
      Confirm the "checking…" feedback appears, followed by the update prompt.
      Click **"Install & Restart"** and confirm the round-trip (see §1 / §2).
- [ ] **5.3** Disconnect from the network. Click **Help → Check for Updates**.
      Confirm a network error is surfaced (not a crash or silent failure).
- [ ] **5.4** Confirm the update prompt / "checking" / "up to date" / error
      feedback is surfaced and dismissible without the flow feeling broken. KNOWN
      papercut: these currently use a blocking alert dialog (must acknowledge)
      rather than a transient banner — if it feels disruptive in practice, file a
      follow-up issue to switch to a non-blocking banner.

---

## 6. Signature-Failure Path

> A tampered manifest or wrong-key signature must be rejected — no update
> applied.

- [ ] **6.1** Serve a tampered `latest.json` (flip a single byte in the JSON
      body). Trigger an update check pointing at this manifest.
      Confirm `fetch_update` returns an error, no download begins, and the
      failure is surfaced to the user (error shown in the prompt or logged
      visibly).
- [ ] **6.2** Serve a `latest.json` signed with a **different** (wrong) minisign
      key. Trigger an update check. Confirm the signature verification fails,
      no download begins, and the failure is surfaced.
- [ ] **6.3** Serve a `latest.json` with a **correct signature but a mismatched
      SHA-256** for the artifact. Trigger an update. Confirm the download
      completes but the SHA-256 check fails and the swap is NOT applied; dat0
      remains at the old version.
- [ ] **6.4** In all three cases above, confirm dat0 remains fully functional
      after the rejected update (no corrupt state, no crash on next launch).

---

## 7. GUI Relaunch Confirmation

> Headless CI cannot verify this; it requires a real display.

- [ ] **7.1** After a successful swap (§1 or §2), confirm the GPUI window
      appears in the relaunched process without any `tokio` runtime or GPUI
      event-loop error in the console.
- [ ] **7.2** Confirm previously open workspace / tabs are recovered (or a
      clean session starts if no workspace was open).

---

## 8. Release Dry-Run

> Full end-to-end sign / publish validation before tagging a real release.

- [ ] **8.1** Complete the production-key provisioning:
      - Generate a passwordless minisign key pair (see
        `docs/security-runbook.md` § "minisign Update-Signing Key").
      - Set `MINISIGN_SECRET_KEY` in the GitHub Actions repository secrets.
      - Commit the new public key to
        `crates/dat0-app/assets/minisign-public-key.txt`.
- [ ] **8.2** Run a `workflow_dispatch` dry-run (skips publish):
      ```bash
      gh workflow run release.yml --field dry_run=true
      ```
      Confirm the build, sign, notarize (macOS), and `latest.json` generation
      steps all pass.
- [ ] **8.3** Verify the generated `latest.json` signature locally:
      ```bash
      minisign -V -p crates/dat0-app/assets/minisign-public-key.txt \
               -m latest.json -x latest.json.minisig
      ```
- [ ] **8.4** Tag a real release and run the full publish workflow. Confirm
      `latest.json` and all platform artifacts appear on the GitHub Release.
- [ ] **8.5** Run the macOS (§1) and Linux (§2) round-trip UAT against the
      published release artifacts.
