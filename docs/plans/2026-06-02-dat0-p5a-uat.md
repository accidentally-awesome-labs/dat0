# P5a — SQL Console: Manual UAT Checklist

> **Status:** OWED (to be run by the user). Created 2026-06-02 at the close of
> P5a (T12). Headless/CI agents cannot drive the GPUI window or read on-screen
> color, so every check below requires a human at a **release build** of the
> app with macOS GUI permissions (Screen Recording / Accessibility) granted.

**Why this exists.** P5a's logic is test-green (see "Automated coverage"
below), but four things can only be confirmed by eyes on the running app:
(1) the runtime SQL syntax highlighting is actually colored, (2) the
first-ever **view-scoped action** dispatch (`Cmd+Shift+C` / `Cmd+Enter` /
`Cmd+.`) really fires the registered handler at runtime, (3) the cancel path
visibly interrupts a live query, and (4) multi-tab + SQL restore across
relaunch. Treat this as the P5a exit gate.

## P5a checklist (9 items)

### 1. Toggle the SQL console — `Cmd+Shift+C`
Press `Cmd+Shift+C`. The console panel appears below the PipelineBar; press
again and it hides.
- **First view-scoped action in the app.** Unlike the global app actions
  shipped earlier, `SqlConsoleToggle` / `SqlRun` / `SqlCancel` are dispatched
  in the view scope. The headless suite cannot prove runtime keystroke
  dispatch fires the registered handler — **confirm the toggle actually
  responds to the keystroke** (not just the View-menu item). If the menu item
  works but the keybind does nothing, that's a real dispatch-wiring finding to
  file.

### 2. SQL keywords are colored
Type a query (e.g. `SELECT id, name FROM users WHERE id > 10;`). Keywords
(`SELECT`, `FROM`, `WHERE`) should render in a **distinct color** from
identifiers/literals.
- This is the **owed visual confirmation** of T0/T4: the runtime
  `tree-sitter-sequel` grammar is registered via `LanguageRegistry` and the
  editor is `code_editor("sql")`. T0 proved the API path compiles + links; it
  could NOT prove pixels are colored.
- **If NOT colored** (plain monochrome text), that is a real finding — file it
  (likely the registry registration didn't run at boot, or the highlight query
  didn't match). Per design decision 7, the documented fallback is plain
  `code_editor` with highlight pushed to a later phase.

### 3. `Cmd+Enter` runs the statement **under the cursor**
Type several `;`-separated statements, e.g.:
```sql
SELECT 1 AS a;
SELECT 2 AS b;
SELECT 3 AS c;
```
Place the cursor inside the **second** statement and press `Cmd+Enter`. Only
`SELECT 2 AS b` runs; its result appears in the **main grid** (table tab).
Move the cursor into a different statement, re-run — the result changes to
that statement's output.
- Run resolves the statement under the cursor via `statement_at(text, cursor)`
  (the splitter respects quotes + line/block comments).

### 4. Selection + `Cmd+Enter` — **N/A (known limitation, not a test to pass)**
"Select a span of text and run **only the selection**" is **not a P5a
feature**. At gpui-component rev `0f0ab35`, `InputState::selected_range` (field)
and `selected_text()` (method) are both `pub(super)` (private to the crate);
the only public state accessor is `cursor() -> usize`. There is no public
selection accessor to read the highlighted span, so the run path is
**cursor-only** (statement under the cursor — item 3).
- **Document as a known limitation, do NOT mark as failed.** A future
  gpui-component bump that exposes a public selection getter (or an upstreamed
  `pub` accessor) would revisit this. See
  `docs/internal/gpui-component-api-notes.md` §6(b).

### 5. `Run ▾ → Run in results pane` — console-owned grid, main grid untouched
Open the `Run ▾` split button and choose **"Run in results pane"**. The query
result renders in the **console-owned pane grid** (inside the console, not the
main table tab). Confirm the **main grid / table tab is unchanged** by this
run.
- Then run a query that returns **> ~1024 rows** (e.g.
  `SELECT * FROM range(50000) t(x)`), scroll the pane grid **past row ~1024** —
  rows keep loading (the pane prefetches **its own** source, independent of the
  main grid's source).

### 6. Long query → spinner + elapsed counter → `Cmd+.` cancels
Run a deliberately slow query, e.g.:
```sql
SELECT count(*) FROM range(100000000) a, range(100000000) b;
```
- A spinner + an **elapsed-seconds counter** ("running… Ns") appears while it
  runs.
- Press `Cmd+.` (or click the **Cancel** button). A muted **"Cancelled"**
  status appears; the grid is **unchanged** (no partial/garbage result).
- Cancellation is **token-free**: a `QueryCancel` drop-guard calls the
  connection-wide `engine.interrupt()`. **This is the D-008 exit check** —
  D-008 flips `in-progress → closed` once this passes.

### 7. Bad SQL → red dismissible error strip
Run invalid SQL, e.g. `SELEKT * FROM nope;`. A **red, dismissible** error
strip appears; the message is **prefixed with the tab title**. Click the **✕**
to clear it.

### 8. DDL → "OK" status line
Run a non-result statement, e.g. `CREATE TABLE t_uat (x INT);`. A muted
**"OK"** status line appears (no grid result, no error). A follow-up
`DROP TABLE t_uat;` should also report "OK".

### 9. Multi-tab + persistence across relaunch
Click **`+`** to add tabs; type **different** SQL in each. Click **`✕`** to
close a tab. Set one tab active, then **quit and relaunch** the app. Confirm:
- the same set of tabs is restored,
- **each tab's SQL text** is restored,
- the **active tab** is restored.
- Backed by session schema **v5** (`migrate_v4_to_v5`); persistence is atomic
  (`Session::persist`).

## Automated coverage (already verified by tests — for context)

The following are **green in CI** and do NOT need manual eyes; listed so the
human knows what's already proven vs. what this checklist still owes:

| Area | Where | What's covered |
|------|-------|----------------|
| Statement splitter + classify | `crates/dat0-app/tests/statement.rs` (13 tests) | `;`-split respecting single-quote / line-comment / block-comment boundaries; `statement_at(cursor)` (under-cursor + trailing-after-last-`;`); classify SELECT / CTE / leading-comment-then-SELECT as result, CREATE / INSERT / empty as exec. |
| Query model | `crates/dat0-app/tests/query_model.rs` (3 tests) | `QueryModel` / `SqlTab` / `ResultTarget` / `ExecState` state shape. |
| SQL console integration | `crates/dat0-app/tests/sql_console_integration.rs` (6 tests) | End-to-end console run → result-binding wiring. |
| Session v5 round-trip | `crates/dat0-app/tests/session_migration.rs` (18 tests) | v1→v5 migration ladder; tabs + active-tab + SQL text persist + restore. |
| Engine VIEW / EXEC round-trip | `crates/dat0-engine/tests/{execute,execute_paged,temp_view_lifecycle}.rs` | result statements → reused TEMP VIEW read via `execute_paged`; non-result via `execute()`. |
| Engine interrupt round-trip | `crates/dat0-engine/tests/interrupt.rs` (2 tests) | `Engine::interrupt()` cancels an in-flight query (the primitive behind the `QueryCancel` drop-guard). |
| Per-source pane cache isolation | results-pane prefetch path | pane grid prefetches its own source; main-grid cache untouched. |
| i18n key parity | `crates/dat0-i18n/tests/basic.rs`, `crates/dat0-app/tests/menu.rs` | every used `sql.*` key resolves to a real string (missing keys surface the key itself). |

**Not covered by tests (this checklist's job):** on-screen syntax coloring
(item 2), runtime view-scoped keystroke dispatch (item 1), the visible
spinner/elapsed/"Cancelled"/"OK"/error-strip UI affordances (items 6–8), and
relaunch persistence as observed in the running window (item 9).
