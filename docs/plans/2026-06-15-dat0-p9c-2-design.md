---

## 1. Framing

P9c-2 builds the **user-facing AI features** on top of P9c-1's secure foundation.
Everything outbound still flows through P9c-1's `transport` + `ssrf` +
schema-only `AiRequest` — this slice adds the *callers* (which assemble real
schema context + prompts) and the *streaming UI*, not new network plumbing.

---

## 2. Scope (from master-spec)

- **NL → SQL chip** in the SQL Console toolbar — natural-language prompt → SQL
  emitted **into the editor**, **never auto-runs** (hard requirement).
- **"Explain" button** next to Run — produces a plain-language explanation of the
  current query (or selection) in a side panel.
- **Streaming side panel** — progressive render of AI responses (SSE deltas →
  `cx.notify` per chunk).

---

## 3. Carried forward from P9c-1 (deferred there, built here)

- **SSE streaming primitive** — `Wire::chat_stream()` over `reqwest`'s already-
  enabled `stream` feature; parse provider SSE (`content_block_delta` for
  Anthropic, `chat.completion.chunk` for OpenAI-compatible). **T0 spike** for the
  GPUI progressive-render loop (off-thread engine work → dispatcher → `cx.notify`
  on each delta; text, so no `!Send`/RenderImage concern like P9a-1 — but confirm
  the spawn/notify shape).
- **Live catalog-schema assembly** — build `SchemaContext` (names + types only)
  from the active workspace catalog/`get_tables`, bounded for the payload filter.
  This is the first real population of P9c-1's `AiRequest.schema`.
- **NL→SQL & Explain prompt assembly** — fixed system instruction + schema context
  + user prompt; resolve Anthropic shape via the `claude-api` skill and
  OpenAI/OpenRouter shape via context7 at build time (do not memorize).

---

## 4. Key decisions to resolve at brainstorm

- **Schema-context bounding** — which tables/columns are sent (active view only?
  whole workspace? user-selectable?) and how it's capped for token budget and the
  payload filter. Confirm it never includes row values (P9c-1 fixture still holds).
- **NL→SQL insertion** — cursor-insert into the editor without running (mirror the
  P5b Save-as-Table / completion insertion idiom); confirm "never auto-runs".
- **Explain target** — explain the whole editor buffer, the selection, or the
  cursor statement? Where does the explanation render — the P9c-1 AI dock, a new
  side panel, or the results pane?
- **Streaming UX** — model + `cx.notify` per delta; supersede-id guard (like the
  inspector/chart load-id) so a newer prompt cancels a stale stream; cancel button.
- **Error/refusal handling** — surface rate-limit / `stop_reason: "refusal"`
  (Anthropic) / OpenAI error bodies as banner/inline; no partial-SQL auto-run.
- **Model capability** — the P9c-1 model field now matters for output quality;
  consider a per-feature model hint (cheap for Explain, capable for NL→SQL).
- **Sub-slicing** — likely shippable as one slice (chip + Explain + streaming
  panel share the streaming primitive), but a chip-first / Explain-second split is
  possible if the streaming T0 spike proves heavy.

## 5. Security (R17 still binding)

- Reuse P9c-1's schema-only `AiRequest`; the new schema-assembly code must keep the
  payload-filter fixture green (no row data / results / file paths unless
  include-sample-rows is explicitly on).
- All outbound still SSRF-gated for Custom; AI still off without a key.

## 6. Risks / unknowns

- **GPUI streaming UX** — front-load into a T0 spike (minimal SSE→panel loop).
- **Provider SSE drift** — Anthropic vs OpenAI-compatible chunk shapes differ;
  resolve both at build time (claude-api + context7).
- **Prompt injection via schema names** — low (names are user's own), but keep the
  system prompt firmly scoped to "emit SQL / explain"; never execute returned SQL.
