# dat0 P10a-2 — In-app auto-update (design)

**Date:** 2026-06-22
**Phase:** P10a-2 (sequel to P10a release pipeline; see `docs/plans/2026-06-17-dat0-p10a-design.md` §1 for the P10 4-way split)
**Status:** design approved; implementation plan to follow (`writing-plans`).

## Goal

Turn P10a's manual *nudge* (About box → open the Releases page → download by hand) into a **one-click "Install & Restart"** updater: a single cross-platform Rust engine that checks GitHub Releases, verifies a signed manifest, downloads the platform artifact, atomically swaps the running app, and relaunches into the new version. User controls *when* (explicit click); no silent background download, no full automation.

**Closes** D-003 (Sparkle SUUpdater bridge) and D-004 (AppImageUpdate subprocess) — **superseded** by the unified-Rust-updater choice, not implemented as originally scoped.

## Locked decisions (from brainstorm 2026-06-22)

- **D1 — UX:** one-click **Install & Restart**. Detect → dismissible "Update available — [Install & Restart] / [Later]" → on click: download → verify → atomic swap → relaunch. Not background-download, not fully-automatic (user controls timing).
- **D2 — Mechanism:** **unified cross-platform Rust updater** (cargo-packager/tauri-updater-style), NOT Sparkle + AppImageUpdate. Avoids the Sparkle framework embed, the objc2 bridge, the Sparkle↔GPUI run-loop spike, and appcast hosting. Source = **GitHub Releases** (reuses P10a distribution + the nudge's existing check); authenticity = a **minisign-signed `latest.json`**. Rationale: since we build our own one-click UI regardless, Sparkle's main advantage (native UI) is moot — we'd only use it as a download/verify/apply engine, which a small Rust module provides without Sparkle's integration risk.
- **D3 — Check policy:** **on launch (background) + manual**. Silent check shortly after launch → if a newer signed release exists, surface the dismissible prompt; plus a manual "Check for Updates…" menu/About action. A **Settings toggle "Check for updates automatically" (default on)** disables the launch check (privacy; ties to P10b's privacy-review doc). The launch check is a single GET to GitHub — no telemetry/PII.
- **D4 — Install-location scope:** **user-writable installs only in v1.** One-click works when dat0 lives somewhere the user can write (`~/Applications`, Downloads, a project folder) and for user-placed AppImages. If the install dir is not writable (e.g. macOS `/Applications`, admin-owned), **detect and gracefully fall back to the P10a nudge** (open Releases). Privileged `/Applications` updates (SMJobBless-style helper) are **deferred**.

## Architecture & components

Grow P10a's `crates/dat0-app/src/update/` module into the real updater; **retire** the obsolete P1 scaffolding `crates/dat0-app/src/updater/{mod,sparkle,appimage}.rs` and `crates/dat0-app/assets/sparkle-public-key.txt`. Pure-first, testable units:

- **`update::manifest`** — `UpdateManifest { version, platforms: { macos, linux } → ArtifactEntry { url, sha256, size } }`; parse `latest.json`; **minisign-verify** the manifest bytes against an embedded public key using `minisign-verify` (pure-Rust, verify-only). *Pure / unit-tested with signed test vectors.*
- **`update::check`** — fetch `latest.json` + `latest.json.minisig` from the GitHub "latest" release assets, verify, and compare versions (reuses the existing `newer_than`). Returns `Option<AvailableUpdate>`. *Unit-tested with a mock server (mockito, already a dev-dep).*
- **`update::download`** — download the platform `ArtifactEntry.url` to a temp file with a progress callback; verify the file's SHA256 against the manifest entry; reject on mismatch. *Unit-tested with a mock server + known-hash fixture.*
- **`update::apply`** — platform-specific **atomic swap + relaunch** (the risky bit — see *T0 spike*). Performs the **writability pre-check**; if not writable, returns a `FallbackToNudge` outcome (no swap). *Pure parts (path/writability/rollback sequencing) unit-tested on a fake bundle; the real swap+relaunch is spike + UAT.*
- **`update::ui`** (app layer, GPUI) — the dismissible "Install & Restart / Later" prompt (mirrors the P10a About/banner pattern), download progress, error surfacing, and the nudge-fallback path. Headless-untestable (UAT-owed, per project norm).
- **Settings** — extend the settings schema with `update.auto_check: bool` (default `true`); a Settings UI row.
- **Menu** — a "Check for Updates…" action (manual trigger, always available even when auto-check is off).

### Distribution & signing (extends P10a's `release.yml`)

- **Linux:** the existing `dat0.AppImage` is directly swappable — the manifest points at it; **no new artifact**.
- **macOS:** a DMG is awkward to auto-apply (mount/copy), so the publish job *also* emits **`dat0.app.tar.gz`** (gzip-tar of the bundled `.app`); the DMG stays for fresh installs. The manifest's macOS entry points at the tarball.
- The publish job generates **`latest.json`** (version + per-platform `{ url, sha256, size }` for the *updater* artifacts) and **minisign-signs** it → **`latest.json.minisig`**; both are uploaded to the GitHub Release.
- **New CI secret:** `MINISIGN_SECRET_KEY` (+ `MINISIGN_PASSWORD`). The **minisign public key embeds in the app binary** (an `include_str!` asset, replacing `sparkle-public-key.txt`). The `security-runbook` documents minisign key storage + rotation (replaces the "EdDSA appcast key is P10a-2" placeholder note from P10a's runbook).
- **Verification chain (defense in depth):**
  1. **Manifest authenticity** — minisign-verify `latest.json` against the embedded pubkey (prevents manifest spoof / version downgrade).
  2. **Artifact integrity** — SHA256 of the downloaded file matches the manifest entry.
  3. **Platform signature (inherent second layer)** — on macOS the swapped `.app` is Apple codesigned + notarized, so **Gatekeeper re-validates it on relaunch**; on Linux the AppImage's GPG `.sig` (already produced by P10a) may be verified. v1 *gates* on (1)+(2); (3) is automatic on macOS.

## T0 spike (gates the plan — the one real unknown)

**Can a running GPUI app atomically self-replace its own bundle and relaunch into the new version?**

- **macOS:** the running executable is mmap'd and can't be overwritten in place. The swap is: **move the running `.app` aside → move the new `.app` in → relaunch via `open` → the old process exits**. The spike proves this works under GPUI **and** that notarization survives the move (it does — we move the intact, already-signed bundle; we don't re-sign).
- **Linux:** replace the AppImage file on disk (the running AppImage is a mounted FUSE image; replacing the backing file is safe), then relaunch via `exec`.
- **Probe:** build a v1 and a v2; have v1 download → swap → relaunch; confirm the new process runs v2 and the old one exits cleanly; on macOS confirm the relaunched bundle is still Gatekeeper-valid (`spctl --assess`).
- **Verdict:** doc-only PASS/FAIL with the concrete swap sequence each platform will use. Mirrors P10a's T0 spike discipline. A FAIL on macOS would narrow v1 to the nudge fallback on macOS (Linux still ships) — recorded as a deferral.

## Error handling & rollback

- **Download/verify failure** → keep the running app untouched, show the error, offer the nudge fallback ("Download update" → Releases page).
- **Apply is reversible** — the move-aside-then-move-in sequence: if moving the new bundle in fails, move the old bundle back (rollback). Never leave the user without a working app.
- **Not writable** → never attempt a swap; fall back to the nudge.
- **Relaunch failure** → the new bundle is already in place and valid; surface "Update installed — please reopen dat0."

## Scope & deferrals

**In scope (v1):** one-click Install & Restart; both platforms (macOS `.app` swap, Linux AppImage self-replace); user-writable installs; launch + manual check with Settings opt-out; minisign-signed `latest.json` verification + SHA256; `release.yml` extension (`latest.json` + `.minisig` + `dat0.app.tar.gz`); the apply/relaunch T0 spike; menu action; a "What's new" link to the release page in the prompt.

**Deferred / out of scope:**
- Privileged `/Applications` updates (SMJobBless-style helper + admin prompt) → **new deferral**.
- Delta / zsync downloads (v1 fetches the full artifact each time).
- Staged / percentage rollout, channels (stable/beta) — beta is already P10c-deferred.
- In-prompt rendered release notes (a link to the GitHub release page suffices).
- Windows auto-update (no Windows build exists yet).

**Register impact:** close **D-003** + **D-004** (superseded by D2); open one new deferral for privileged `/Applications` updates.

## Testing

- **Pure / unit:** manifest parse + minisign verify (signed test vectors, incl. a tampered-manifest rejection and a wrong-key rejection); SHA256 verify (match + mismatch); version compare (reuses P10a's `newer_than` tests); writability detection; apply-sequence reversibility/rollback on a fake bundle dir; nudge-fallback decision logic.
- **Mock-server:** `check` (fetch + verify `latest.json` + `.minisig`) and `download` (fetch + SHA256) against a local mockito server.
- **Spike + manual UAT:** the real swap + relaunch (headless can't relaunch a GUI app) — joins the standing UAT backlog with a dedicated `docs/plans/2026-06-22-dat0-p10a-2-uat.md`: clean-VM update from a real older signed release to a newer one on both OSes, the not-writable fallback, the Settings toggle, and the manual menu action.

## Self-review notes

- **Dependencies:** `minisign-verify` (pure-Rust, verify-only — app embeds pubkey, never the secret); `sha2` (confirm present or add); `flate2` + `tar` for `.app.tar.gz` extraction (confirm/add). `ureq` (existing) for downloads. The signing side uses the `minisign`/`rsign2` CLI in CI, not in the app.
- **Reuse:** the P10a `update::{newer_than, fetch_latest, LATEST_RELEASE_API}` nudge stays as the fallback path; the auto-updater is the layer above it.
- **Non-goals correctly absent:** auto-without-consent, background download, Sparkle/appcast, Windows, delta updates, channels.
