## 1. Context — where P10b sits in the P10 split

P10 ("Hardening + perf gates + signing", master spec §21.2) is the largest roadmap
phase — seven mostly-independent subsystems. It was brainstormed 2026-06-17 and split
four ways:

- **P10a** — release pipeline (signed/notarized macOS DMG + signed Linux AppImage +
  About box + `.dat0` association + update-nudge + runbooks). **MERGED** 2026-06-21
  (PR #29, squash `13460e5`).
- **P10a-2** — in-app auto-updater (minisign-signed `latest.json` → one-click
  Install & Restart). **MERGED** 2026-06-23 (PR #30, squash `4ece125`).
- **P10b** — **this slice:** a11y audit checklist + `docs/a11y.md` + AccessKit
  re-check (D-015) + Settings §24.2 completeness gate + privacy docs.
- **P10c** — externally-gated tail: GPU perf-gate runner (D-013), GlitchTip
  crash-submission flip + end-to-end verification, beta channel. **Deferred** until
  the dedicated Mac/GPU hardware, the GlitchTip instance, and a tester cohort exist.

The dividing line for P10b is **"everything in P10 scope that is fully buildable and
verifiable on the existing dev/CI substrate, with no external hardware, no live
GlitchTip instance, and no beta testers."** Each P10b workstream lands and gates
without waiting on an external dependency.

## 2. Scope & boundary

**In scope:**

1. **A11y audit** — an automated WCAG-2.1 contrast gate (computed from the three
   builtin theme token files), re-tuning the one failing real pair until all three
   themes pass, a manual keyboard-reachability audit, and the documented
   screen-reader stance. Deliverable: `docs/a11y.md` + a CI contrast test.
2. **Settings §24.2 completeness** — **mount the real Settings window** (the Settings
   panel is a never-mounted stub today: `open_settings_window` only logs, and all four
   existing sections render `div().child(t("…placeholder"))` with no real widgets) and
   grow it from 4 to the 9 sections required by §24.2, with **real `gpui_component`
   widgets** in every section, using a "hub + thin section" model. This finally
   discharges the long-deferred "T13 wires the real settings window."
3. **Privacy docs** — author `docs/privacy.md` (user-facing "what we collect") and
   `docs/privacy-review-process.md` (the per-release privacy review checklist).
4. **AccessKit re-check (D-015)** — re-verify AccessKit's absence on the pinned
   GPUI and record the result.
5. **UAT doc** — `docs/plans/2026-06-23-dat0-p10b-uat.md` carrying the manual
   checklist that the gate requires ("verified by manual checklist").

**Out of scope — deferred to P10c (externally gated):**

- GPU perf-gate self-hosted runner + enforcing the perf-budget benches as merge
  gates (D-013).
- Flipping crash submission from "captured locally" to "submit to GlitchTip" and
  the GlitchTip end-to-end verification (no GlitchTip instance exists yet).
- The beta channel and tester cohort.

Note the boundary inside the telemetry concern: P10b ships the **Telemetry Settings
section and its opt-in toggle surface** (needed for the §24.2 completeness gate), but
the actual submission-path flip and end-to-end verification stay in P10c. The toggle
persists the user's preference; the submission path remains local-capture-only until
P10c configures the backend.

## 3. Workstream A — A11y audit

### 3.1 Current state (verified 2026-06-23)

- Three builtin themes ship as JSON token files under
  `crates/dat0-app/src/theme/builtins/`: `light.json`, `dark.json`,
  `high-contrast.json`. Each defines seven style tokens: `background`,
  `foreground`, `border`, `accent`, `error`, `success`, `warning`.
- All three use the GitHub Primer palette. Pre-computed WCAG ratios show that
  `foreground`/`background` and every status-color-on-`background` pair already
  clear 4.5:1 in all three themes (the tightest is the light theme's
  `warning` at ≈4.87:1).
- The operability a11y baseline (full keyboard navigation of the selection model,
  visible focus ring) shipped across P4b/P4c/P5c. AccessKit is absent (see §5).

### 3.2 Contrast gate

A new pure module `crates/dat0-app/src/theme/contrast.rs` implements WCAG 2.1
relative-luminance and contrast-ratio math over hex color strings. No external
dependency; it parses the existing token hex values.

The gate is a `#[test]` that loads all three builtin theme JSON files and asserts
that every pair in the matrix below clears its threshold. It runs headless (pure
arithmetic over JSON), so it gates in CI on both platforms with no GPUI surface.

**Contrast pair matrix (per theme):**

| Pair | Threshold | Rationale |
|---|---|---|
| `foreground` on `background` | ≥ 4.5:1 | primary body text (WCAG AA normal text) |
| `error` / `success` / `warning` on `background` | ≥ 4.5:1 | status text |
| `accent` on `background` | ≥ 4.5:1 | link / interactive text |
| `foreground` on `accent` | ≥ 4.5:1 | selected-row / selected-cell text (the risky midtone-on-midtone pair) |
| focus-ring color on `background` | ≥ 3:1 | non-text UI component (WCAG 1.4.11) |
| plain `border` / dividers | **exempt** | decorative; not the sole means of identifying a control (WCAG 1.4.11 carve-out) |

The `border` token is deliberately **exempt**: borders/dividers in dat0 are
decorative and never the sole indicator of a control's state, so the WCAG 1.4.11
non-text-contrast requirement does not apply. Including it would force an
appearance-altering re-tune for no accessibility benefit.

The focus-ring color is whatever the running app actually paints as the focus ring
(established in P4b — a per-cell focus ring). The audit identifies that token and
includes it in the matrix; if it is the `accent` token, the `accent`-on-`background`
row already covers it.

### 3.3 Fix failures (in scope) — measured

The exact failing set was computed 2026-06-23 (WCAG 2.1 math over the actual token
hex values). Result:

| Pair | light | dark | high-contrast | verdict |
|---|---|---|---|---|
| `foreground` / `background` | 15.80 | 12.25 | 21.00 | all pass |
| `error` / `success` / `warning` / `accent` on `background` | 4.87–5.36 | 5.64–7.49 | 5.25–19.56 | all pass |
| **`foreground` / `accent` (selection text)** | **3.04** | **1.64** | **1.07** | **fails all 3** |
| `border` / `background` | 1.45 | 1.55 | 21.00 | fails light+dark — **exempt** |

So the entire fix scope is **one pair**: selected-row / selected-cell text that paints
`foreground` on the `accent` background fails 4.5:1 in every theme. The fix is **not**
to distort the recognizable `accent` hue — it is to add a per-theme
**`selection_fg`** (a.k.a. `on_accent`) token used only for text painted on an accent
fill, and repaint the selection text site with it. Computed passing values:
light → `#ffffff` (5.19:1 on `#0969da`), dark → a near-black (black-on-`#58a6ff` is
8.3:1), high-contrast → `#000000` (19.56:1 on `#ffff00`).

The a11y task **first inspects how selection is actually painted** (the P4b focus-ring
/ selected-cell render site) so the contrast matrix tests the pair the app really
renders; if selection already uses a non-`foreground` color or a tinted background
that preserves `foreground`/`background` contrast, the token addition is unnecessary
and the matrix is adjusted accordingly. `border` stays exempt (decorative; WCAG
1.4.11 carve-out). This is a small, enumerated, design-sensitive change — a token plus
one paint site — not a palette overhaul.

### 3.4 Keyboard-reachability audit (manual)

A manual walk of every interactive element — menus, the data grid (all selection
variants), the SQL console, the Catalog tree, the Inspector, the Connections panel,
the AI panel, every dialog, and all nine Settings sections — confirming each is
reachable and operable by keyboard alone, with a visible focus indicator. Results
recorded as a pass/fail table in `docs/a11y.md`. This cannot be automated headless
because, without an AccessKit adapter, the GPUI element tree is not introspectable.

### 3.5 Screen-reader stance (documented)

`docs/a11y.md` documents screen-reader compatibility as **accepted out-of-scope for
v1, with rationale**: AccessKit is entirely absent from the pinned GPUI 0.2.2 and
gpui-component 0.5.1 (no `accesskit` dependency, no accessibility node, no adapter),
so a screen-reader-navigable semantics tree is not exposable without forking GPUI.
Master spec §21.2 explicitly permits this resolution ("Screen-reader compatibility
documented (or accepted out-of-scope for v1 with rationale in `docs/a11y.md`)"). The
v1 accessibility story is therefore **operability** (full keyboard navigation +
visible focus + AA contrast), with the screen-reader tree tracked as D-015 for a
future GPUI pin.

### 3.6 Deliverable

`docs/a11y.md` containing: the audit checklist (mapped to the master-spec gate items),
the measured contrast ratios for all three themes, the keyboard-reachability pass/fail
table, and the documented screen-reader rationale. Plus the `theme::contrast` module
and its CI gate test.

## 4. Workstream B — Settings §24.2 completeness (mount real window + hub/thin)

### 4.1 Current state (verified 2026-06-23, all three scouts)

`settings_ui/sections/mod.rs::all_sections()` registers **four** sections (Profile,
Theme, Workspace = Networked Workspaces, Updates); §24.2 requires **nine** (adds
Memory Budget, MotherDuck, AI, Telemetry, Advanced). But more fundamentally: **the
Settings panel is a never-mounted stub.** `settings_ui::open_settings_window` (wired to
the `settings.open` action + the View → Settings menu item) only calls
`tracing::info!("…stub — T13 wires the real window")`. Every section's `render` returns
`div().child(t("…placeholder"))`. No interactive widget exists anywhere in Settings.
So "each section has a working surface" fails at the most basic level today.

The substrate the mount builds on (all verified against real code):

- **Widgets available** at gpui-component 0.5.1 / rev `0f0ab35`: `Button`
  (`Button::new(id).label().primary()/.ghost().disabled(b).on_click(cx.listener(...))`)
  and `InputState` (eager `InputState::new(window, cx)`, stored as `Entity<InputState>`,
  read via `.read(cx).value()`). **No `Switch`/`Checkbox`** and **no ergonomic
  `Select`/dropdown** are shipped — confirmed absent in the API notes and unused
  anywhere in the app. Toggles are therefore built DIY from `div().id().on_click()`
  (the `connections/panel.rs` `action_button` pattern), and fixed-option pickers use a
  **`Button` cycle** (the chart-type toolbar pattern, `window.rs:3467`).
- **Window mount** (`open_window_view`, `window.rs:1010`): `cx.open_window(WindowOptions
  { titlebar: Some(TitlebarOptions{ title }), .. }, |window, cx| cx.new(|cx|
  Root::new(view, window, cx)))`. The `Root` wrapper is mandatory; the Reset-confirm
  dialog needs `Root::render_dialog_layer(window, cx)` mounted in the panel's render.
- **Confirm dialog**: `cx.active_window()?.update(cx, |_root, window, cx|
  window.open_dialog(cx, |d,_,_| d.title(..).confirm().child(body).on_ok(..).on_cancel(..)))`
  (`use gpui::ParentElement as _`).
- **Settings struct** already carries `telemetry.crash_submission_enabled` (default
  false, read at `boot.rs:64` → `Telemetry::init`). **Missing fields to add:**
  `memory_budget_mb: u32` (default 1024) and `log_level: String` (default
  `"info,dat0=debug"`).
- **Dock launch**: the AI and Connections panels are toggle-only docks on
  `WorkspaceShell` (`toggle_ai_panel(cx)` / `connections_panel_visible`), reachable
  from a separate window via `window_registry::focused_workspace_weak()`.

### 4.2 Architecture: mount a real Settings window (the deferred "T13")

The stateless `SettingsView` + `SettingsSection::render(&self, window, app)` trait
cannot hold an `InputState` (which must be eagerly constructed with `&mut Window` and
stored as an entity). So Settings becomes a **stateful `SettingsPanel` GPUI entity**,
opened as a **dedicated window** (replacing the `open_settings_window` stub, matching
its original "dedicated window" intent and scout 1's ready `open_window_view`
template). `SettingsPanel` owns: `selected_section: String`, the `Entity<InputState>`
widgets it needs (author name, author email, memory-budget number) plus their
subscriptions, and a `SettingsStore` handle.

> **Decision (window, not dock).** Settings opens as its own window, not as an in-shell
> dock like the other panels. Rationale: it matches the existing stub + the spec's
> "Settings panel" being a discrete surface + the Cmd-, desktop convention, and it
> avoids growing the already-large `WorkspaceShell::render`. Trade-off: the thin AI/MD
> launch buttons toggle a dock in the *focused workspace window* (via
> `focused_workspace_weak()`), so the user switches to the main window to see it — an
> acceptable v1 behavior. (Flag at spec review if you'd prefer an in-shell dock.)

The `all_sections()` registry stays as the source of truth for the **sidebar list +
order + labels + the completeness test**, but rendering moves into per-section methods
on `SettingsPanel` (`render_profile`, `render_theme`, …). The existing store-only
persistence free functions (`set_treat_all_as_networked`, `set_update_auto_check`,
`ProfileSection::on_name_change`, …) are **reused unchanged** as the persistence layer
the new widgets call on change — preserving every tested round-trip contract.

### 4.3 Section-by-section widget mapping (nine sections, §24.2 order)

| # | Section | Widget(s) | Persists to |
|---|---|---|---|
| 1 | Profile | two `InputState` (name, email) | `author.name` / `author.email` (exists) |
| 2 | Theme | `Button` cycle over the 3 builtins → `Theme::switch(cx, id)` live | `theme.id` (exists) |
| 3 | Memory Budget | `InputState` (MB number) + "applies to new windows" footnote | **new** `memory_budget_mb` |
| 4 | MotherDuck (thin) | status line (`md_status()`) + `Button` "Manage connections…" | — (launches dock) |
| 5 | AI (thin) | status line (`is_ai_ready()`) + `Button` "Configure AI…" | — (launches dock) |
| 6 | Telemetry | DIY toggle (default off) + link `Button` to privacy doc | `telemetry.crash_submission_enabled` (exists) |
| 7 | Networked Workspaces | DIY toggle | `workspace.treat_all_as_networked` (exists) |
| 8 | Updates | DIY toggle | `update_auto_check` (exists) |
| 9 | Advanced | Diagnostics `Button`s + Reset `Button`→confirm dialog + log-level `Button` cycle | **new** `log_level` |

**Real sections** (genuine new controls): Memory Budget, Telemetry, Advanced. **Thin
sections** (status + launch button, no rich-panel duplication): MotherDuck, AI. The
existing four (Profile, Theme, Networked, Updates) finally get their real widgets too
(this is the discharge of "T13").

**Memory Budget** — `InputState` MB number → new `Settings.memory_budget_mb` (default
1024). A single read-once helper feeds the seven hardcoded `1024*1024*1024` callsites
(`window.rs:252,322,1072,1107,1115,1252,1254` → `Session::new/recover(.., budget_bytes)`).
"Applies to new windows" footnote; closes D-014's editable path (live-reapply = v1.x).

**Telemetry** — DIY toggle bound to the existing `telemetry.crash_submission_enabled`;
link button to `docs/privacy.md`. Copy makes clear submission activates only when the
GlitchTip backend is configured (P10c); the flag itself already gates `Telemetry::init`.

**Advanced** — Diagnostics ("Open log folder", "Reveal config directory" via
`platform::open_url(path)`; read-only version + git-sha from `BuildInfo::current()`);
Reset-to-defaults `Button` → `window.open_dialog(...).confirm()` → writes
`Settings::default()`; log-level `Button` cycle (error/warn/info/debug) → new
`Settings.log_level`, read in `boot::init_logging` (applies next launch; addresses
PD-001 by choosing a directive that matches the dat0 crates).

**Thin MotherDuck / AI** — status line from `ws.connections.md_status()` /
`ws.is_ai_ready()`, and a `Button` whose `on_click` resolves
`focused_workspace_weak()` → `entity.update(cx, |shell, cx| shell.toggle_*_panel(cx))`.

### 4.5 T0 spike (gates the plan)

Before building nine sections, a **T0 compile-and-render spike** proves the load-bearing
unknowns at the pinned rev in one throwaway skeleton: open a real `SettingsPanel`
window via `cx.open_window` + `Root::new`; render one `InputState`, one DIY toggle, one

## 6. Workstream D — Privacy docs

**`docs/privacy.md`** — the user-facing "what we collect" page, source-of-truth in the
repo per master spec §15.5, linked from the Telemetry toggle. Mirrors §15:
- v1 stance: local error capture always (rotating logs, redacted paths); crash
  submission opt-in, default off; no usage analytics; no version-check ping (§15.1).
- What's transmitted when opt-in is on: stack trace, OS + version, dat0 version,
  optional free-form user note (§15.2).
- What is never transmitted: schema/column names, query text, query results, file
  paths, source/derived data, `.dat0` contents, AI prompt content, BYOK keys,
  MotherDuck token (§15.3).
- Backend: self-hosted GlitchTip, never third-party SaaS (§15.4).

**`docs/privacy-review-process.md`** — the per-release privacy review checklist (master
spec §21.2 deliverable). Defines the review run before each signed release:
- `before_send` redaction path verified (no schema/column/query/path/key leakage).
- AI request payloads confirmed schema-only (the P9c schema-only payload filter).
- SSRF guards confirmed (the P9c provider-URL validation).
- The transmitted/never-transmitted contract (§15.2/§15.3) re-checked against current
  code.

## 9. Risks

- **Settings window mount is the dominant scope** (the deferred "T13"), not a 4→9
  section add as the first design draft assumed. Mitigation: the §4.5 T0 spike
  compile-proves the window + every widget kind before any section is built; the
  registry + tested `set_*` persistence fns are reused, not rewritten.
- **No `Switch`/`Select` in gpui-component** — toggles and pickers are DIY (div+on_click
  toggle, Button-cycle picker). Mitigation: both patterns already exist in-app
  (`action_button`, chart-type cycle); no new primitive is invented.
- **Thin AI/MD buttons reach across windows** via `focused_workspace_weak()`. Risk: a
  null weak handle (no workspace open). Mitigation: button is a no-op + logs when the
  weak upgrade fails; never panics.
- **"Fix failures" scope** — fully enumerated (one pair: selection text); the only
  open question is the real paint site, which the a11y task inspects first. Mitigation:
  add a `selection_fg` token (serde-defaulted so custom themes don't break), don't
  distort `accent`.
- **Thin sections must reuse, not relocate** the MotherDuck/AI panels — a regression
  there would break P5c/P9c surfaces. Mitigation: thin sections only hold a status
  read + a launch button; zero connection/provider logic moves.
- **Telemetry toggle is wired but the backend is a no-op until P10c** — the UI must
  not imply submission works. Mitigation: explicit copy ("…will be sent once a backend
  is configured") and the default-off state.
