transforms — `Reorder` / `Rename` / `DeleteColumn` (T0) — that fold into the grid
`ColumnView` and the export projection but **never touch `compile_view_sql`**, so
the P4a/P4b data-view hot path is byte-for-byte unchanged. On top of that: a

Parquet, T1), the `ColumnView` projection fold (`fold_columns`, T2), a past/
present/future undo **history zipper** with `jump_to`/`remove_at` + a display-only

allowlist + active-stack-only persistence, T4), the grid wired to render through
the `ColumnView` with screen-col→source addressing (T5), header grip
drag-reorder (T6), inline header rename (T7), delete-column via context menu
(T8), the **PipelineBar** collapsed pill strip + expanded timeline with scrubber-

select-column (T13), and the `window.rs` grid-edit extract into `grid/edit_ops.rs`
+ the inline editor `FocusHandle`/focus-on-mount + `Enter` commit-advance (T14).

The headline design bet — **projection is display-only** — held end to end: the
new `projection_e2e` (T15) drives a real `DuckDBEngine` through reorder → rename →
delete → filter → export → remove → undo → persist → restore and confirms each

`view_regen` heavy bench is therefore structurally guaranteed green (see Bench

### Notable plan-quality review catches (the two big ones)

**Plan-quality lesson 1 — T3's plan code shipped a latent undo/redo bug.** The
display-only `ViewChange { new_active_view: Some, sql: None }` shape is reachable
via undo/redo (undoing a projection op recompiles to the same data SQL), but the
wired consumer `run_view_change_inner` would `bail!` on a `(Some, None)` shape —
and the plan's fast-path set `previous_active_view` to the *same live view name*,
which the Phase-4 drop step would then **drop the still-bound view**. Caught by
the T3 code-quality review. Fixed by (a) making the consumer treat `(Some, None)`
as an engine no-op (refresh headers, no rebind, no drop), (b) setting
`previous_active_view: None` on the display-only path so nothing is dropped, and
(c) adding the `undo_of_projection_op_is_display_only_with_no_drop` +
`undo_of_redundant_op_is_display_only` regression tests (`history_zipper.rs`).
`projection_e2e` now also drives this path against a real engine (Stage 7 undo).

**Plan-quality lesson 2 — T5's plan omitted `cell_render` from the `_for_source`
wrapper list.** The plan listed the header/addressing wrappers to route through
the `ColumnView` but forgot the body-cell renderer. The result: the grid **header
order** came from the ColumnView (correct after a reorder/delete) but the **body
cells still painted in SCHEMA order** — so a reorder or a delete would paint cell
values under the wrong headers. This was **invisible to the identity-only test
suite** (where display order == schema order, so the bug is a no-op). Caught by
the T5 code-quality review. Fixed by adding `cell_render_for_source` (look up the
source column for a screen index via `source_for_screen_col`, then render that
column's value) + a **non-identity** regression test
`reordered_column_view_paints_by_source_not_ordinal`.

## Bench numbers (view_regen parity)

No new perf gate in P4c. The P4a/P4b `view_regen` baseline must stay green, and
P4c guarantees this **structurally**, not just empirically:

- **Structural guarantee.** Option B leaves `compile_view_sql` **byte-identical** —
  the three projection variants (`Reorder`/`Rename`/`DeleteColumn`) are explicit
  no-ops in the `compile_view_sql` match arm (`render.rs`), so a stack of
  filter/sort (+ any number of projection ops) compiles to the exact same flat SQL
  P4a emitted. This is pinned by the T0 parity test
  **`edit_render::projection_ops_are_sql_noops_flat_parity`** (asserts the
  projection-laden stack and the projection-free stack compile to the same string).
  The grid `ColumnView` and the export `SELECT` apply the projection *display-side*
  via `fold_columns` / `render_export_select`, never in the data view.
- **Empirical confirmation (PR #9 `run-heavy`, linux-x86, 2026-06-01).** The
  `view-regen-bench` job ran both `view_regen` cases on the PR:
  - `t1_create_view_plus_t2_first_page` (1M-row filter → first page): **308 ms**
    median (306.86 / 308.25 / 309.86 ms) — **under the 500 ms gate**, consistent
    with the P4a linux-x86 ~295 ms baseline.
  - `t1_plus_t2_plus_t3_last_page` (3-transform stack paged to the **last** page of
    1M rows): **882 ms** median (876.71 / 882.45 / 889.68 ms).
- **On the 500 ms "gate" — two caveats, so this number is read correctly:**
  1. **It is advisory, not enforced.** The CI job is `cargo bench … | tee log` +
     artifact upload, with **no threshold-assert step** — `cargo bench` exits 0
     regardless of timing, so a green `view-regen-bench` check means "the bench ran
     and uploaded," **not** "every case met 500 ms." The 500 ms figure is a
     human-review convention (read the number here / in the artifact), not a hard
     fail.
  2. **The 882 ms case is not a P4c regression, and the gate was only ever the
     first-page case.** `t1_plus_t2_plus_t3_last_page` is a pre-existing P4a bench
     case (P4c added none); paging to the last page of a filtered+sorted 1M-row
     view is DuckDB-execution-bound and was ~the same in P4a. Because Option B
     keeps `compile_view_sql` byte-identical, the data SQL — and thus DuckDB's
     execution cost — is unchanged from P4a on both cases. The "1M-row filter
     < 500 ms" exit criterion maps to the **first-page filter case (308 ms ✓)**;
     the multi-transform last-page case is informational, not a 500 ms target.
  P4a baselines for reference: macOS-arm 229 ms p95 / linux-x86 295 ms upper-95% CI
  (first-page filter case). **No regression on any path** (projection ops add zero
  work to the data view).

## Lessons learned

1. **A display-only fast path is a drop-hazard magnet.** The single highest-value
   catch (PD/plan-quality lesson 1) was that the `(Some, None)` `ViewChange` —
   reachable via undo/redo, not just via a fresh projection `apply` — could make
   the consumer drop a still-bound view. The invariant "a change that creates no
   SQL must drop no view" needed to be enforced at BOTH the producer
   (`previous_active_view: None`) and the consumer (`bail!` → no-op). When a code
   path can be reached two ways (apply *and* undo/redo), test both ways.
2. **Identity-only test suites hide ordinal/source confusion.** T5's body-cell
   bug (lesson 2) was invisible because every test used identity display order, so
   "paint by ordinal" and "paint by source" produced the same pixels. The fix was
   a deliberately **non-identity** test (reorder, then assert cells follow source,
   not screen position). Any feature that decouples display order from schema
   order needs at least one non-identity fixture or the decoupling is untested.
3. **`projection_e2e` against a real engine + real COPY caught nothing new — and
   that's the point.** The logic kernels (`fold_columns`, `build_export`,
   `render_export_select`, the zipper) were all unit-tested; the E2E confirmed they
   compose correctly through a live `DuckDBEngine`, a real materialized rowid table,
   and a real CSV read-back (surrogate actually stripped on disk, header actually
   `amt,City`, exactly one filtered row). End-to-end tests earn their keep as
   *composition* guards even when each unit is green.
4. **A queue with only test-side drains is a silent dead-letter (PD-021).** The
   `error_ux::PENDING` queue has existed since P2 (PD-007) with the documented
   intent that "the render layer drains on first window open." That drain was never
   wired, and every phase since has pushed into it (boot, import, session, paste,
   and now export) with no on-screen surface. P4c export UX is the first feature
   where the gap is *user-facing* (you export a multi-GB file and see no
   confirmation). A `push` API with no production `drain` is a smell worth a grep at
   feature-design time.
5. **"Adapt the assertion to real behavior, don't fake it" applies to E2E
   ordering.** The plan's idealized stage order (Reorder→Rename→Delete→Filter, each
   `apply` display-only) does not hold for the FIRST op on a fresh tab — the
   display-only fast path only fires once an active view exists. The E2E
   establishes the data view with the row-dropping `Filter` first, then layers the
   projection ops (each genuinely display-only), keeping every stage assertion the
   plan asked for while matching the real `regenerate_view` contract. The
   adaptation is documented in the test's module doc.

## UAT — runtime smoke (the manual gate is below)

The P4b automated runtime smoke (the tokio-runtime-not-entered ship-blocker) is
fixed and the app launches/imports/renders without panic. P4c adds GPUI-render
surfaces (drag-reorder, inline rename, PipelineBar, export dialog, marching-ants)
whose pixels are **not** exercised by the test suite (no headless GPUI render
harness exists). So the visual + cross-app + keyboard parts remain the user's
manual gate below.

**Important — the banner-host gap (PD-021) affects how UAT reads export
results.** Because `error_ux::PENDING` is never drained at runtime, export success
and failure currently show **NO on-screen banner / toast**. During UAT, verify the
exported **FILE on disk** (it exists, has the right header/rows, omits
`__dat0_rowid`) — do **not** wait for or expect a success toast. Same caveat for
the paste-reject banner (it won't appear; verify the cell outcome directly).

## Manual UAT runbook (the P4 exit gate — to be run by the user)

Needs macOS GUI permissions (Screen Recording / Accessibility) + Excel.app +
Google Sheets — the agent shell cannot drive these. Run against a release build.

1. **Projection.** Import a CSV. Drag-reorder columns by the header grip; double-
   click a header to rename a column; right-click → "Delete Column" on another.
   Confirm the grid reflects each (cells follow their headers after reorder/
   delete — this is the lesson-2 path). Undo each (Cmd+Z). The PipelineBar shows
   one pill per op; remove a *middle* pill and confirm the later ops survive
   (source-identity rebinding).
2. **Export.** File → Export… → for each format **{CSV, JSON, Parquet}** × each
   scope **{Current view, Full table}**: open the output and confirm —
   - **Current view** reflects the active filter/sort/rename/reorder/delete and
     **omits `__dat0_rowid`**;
   - **Full table** is the raw base **minus** the surrogate;
   - a **multi-GB** fixture streams to disk **without OOM** (COPY is streaming).
   Verify the FILE on disk for each — **there is no success toast** (PD-021).
3. **TSV round-trip — Excel & Google Sheets (owed from P4b).** Copy a
   *discontiguous* range whose cells contain tabs, newlines, double-quotes, and
   unicode → paste into **Excel** AND **Google Sheets**; confirm cell-exact
   placement. Copy a block back from each into dat0 → confirm cell-exact round-trip
   with coerce-or-skip on type-incompatible cells (the reject **banner won't show**
   — PD-021 — so verify the skipped cells directly in the grid).
4. **Keyboard-only sweep (owed from P4b).** Arrows (move), Shift+arrows (extend),
   Cmd/Ctrl+arrows (jump-to-edge), Cmd/Ctrl+A (select-all), Escape (clear);
   Enter/F2 (edit) + Enter/Tab (advance — note Tab is the input's own tab-stop, not
   commit-advance, per PD-020); Cmd/Ctrl+C/X/V, Delete (set-null), Cmd/Ctrl+D
   (fill-down); header-click → select-column; gutter → select-row (note: gutter-
   click is **unwired**, PD-019 — select-row is keyboard/programmatic only).
   Confirm the focus ring tracks the active cell.
5. **Crash / restore.** Apply reorder + rename + delete + a filter + a cell edit;
   force-quit; relaunch → the active stack restores, the grid shows the **projected
   + edited + filtered** state, and the PipelineBar matches.

Record results here when run. **Do not consider the TSV + a11y (keyboard) exit
criteria fully met until both UAT directions pass** (carried forward from P4b).
