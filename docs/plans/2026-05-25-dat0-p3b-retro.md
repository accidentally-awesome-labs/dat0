## Plan defects discovered (PD-NNN)

- **PD-011** — P3b plan §3.7 + spec §3.7 ambiguity rule referenced sniff outputs DuckDB doesn't actually expose: there are no candidate-delimiter scores, no encoding column in `sniff_csv` output, and the `Columns` STRUCT array has only `(name, type)` — no per-column confidence. **Found at T0 spike** (`09c570e`) by reading the real DuckDB sniff surface (`duckdb-arrow-api-notes.md` §SniffCsv). **Closed by T9** (`8303b50`): T9 substituted the spec-compatible dual-sniff + UTF-8-heuristic rule documented in PD-011's "What P3b T9 must do instead" section. Severity: low. Status: open in `docs/deferrals.md` (spec §3.7 wording still drifts — left open as a spec-amendment item for the next phase's spec cleanup pass; the *code* matches what the spec *meant*).
- **PD-012** — `NYC_TAXI_SHA256 = "FILL_AT_T8"` placeholder in `crates/dat0-app/src/sample_data.rs`. **Found at T8** (`a075e7f`): the fetch path is wired + tested end-to-end via mockito, but the release asset upload (maintainer-owned) hasn't landed, so the real SHA-256 is unknown at code-author time. The placeholder produces a predictable "checksum mismatch" Banner + Retry UX on a real fetch attempt — the failure path is the production-correct UX. **Open**, scoped to a one-line maintainer follow-up commit after the GitHub Release asset upload (`shasum -a 256 nyc_taxi.parquet` → replace the placeholder). Severity: low.

**Non-PD lessons / minor follow-ups:**
- **T9 follow-up** (`e1fc14e`): the initial T9 import-wizard commit (`8303b50`) wired the drawer + the ambiguous-sniff predicate but forgot to consume the wizard's `OpenWizard` outcome at the call site. ## Lessons learned

1. **Plan-snippet drift recurrence (P3a Lesson 3, again).** PD-011 (sniff outputs that don't exist) and PD-012 (release-asset SHA placeholder) are both expressions of the same risk class: a spec or plan snippet that references an upstream surface (`sniff_csv` output shape, a GitHub Release asset) the implementer can't verify without reaching out. T0 spike caught PD-011 by reading the actual DuckDB docs page + duckdb-rs source, exactly as the P3a retro recommended. T0 spike is now formally the spot where this risk class gets paid down — keep it as a non-skippable phase step.
2. **Drawer / Select / Input widget mount → T13 follow-up.** P3b's T11 Settings widgets and T9 import wizard drawer both ship with the data plumbing live + tested via the underlying state callbacks, but the visible widget mount itself rides on additional gpui-component primitive verification deferred to a T13 follow-up. The retro recommendation: when a phase ships "view stubbed + state-plumbing live + tests on the closure", surface that gap explicitly in the exit-criteria table (we did, with PARTIAL on exit #1 carried over from P3a — same pattern).
3. **Theme global propagation is cleaner than per-window observer wiring.** D-002 closed in T12 with `cx.set_global::<Theme>` + `cx.observe_global`. Cross-window propagation came for free — the app-scoped global was a smaller blast radius than P3a's worry suggested (P3a retro Rec #5 listed it as "untested in this codebase"). Future global-state surfaces (action registry, etc.) should default to the same pattern unless there's a specific reason a per-window observer is needed.
4. **Single-day combined-verify cadence held.** The plan budgeted full two-stage review on T0/T1/T3/T8/T9 and combined-verify on the rest. The implementation log (15 commits, 16:17 → 18:55 ET) bears that out; no task overran its budget except T9 (which needed the OpenWizard-outcome follow-up). The two-stage / combined-verify split from P3a transfers cleanly to UX-polish phases.
5. **Bench-against-real-widget is genuinely intractable headlessly.** P3a retro Rec #5 hinted at this; P3b T13 confirms it. The macOS CI bench artifact continues to track `render_cell` dispatch — the same path the real `GridTableDelegate` calls through — so the regression-detection signal remains intact even if the absolute number under-counts the full chain. P10 perf-budget runner is now formally the place where the full-chain bench lives.
6. **Spec-vs-plan-vs-deferrals consistency at T13.** P3a retro Lesson 5 ("spec is authoritative for filenames + paths") generalized: at T13, the retro-author cross-checks the spec §6 exit-criteria table against `docs/deferrals.md` (closed-during + opened-during) + the actual commits. Any drift between those three sources is a defect. P3b found one minor drift: spec §3.7's ambiguity rule wording still doesn't match what T9 actually implements (PD-011 stays open as a spec-amendment item).

## Recommendations for P4 (transforms)

1. **`ActionRegistry` is ready for non-window-bound actions.** T3 (`abd4182`) ships seven built-in descriptors with `dispatch: Arc<dyn Fn(&mut App) + Send + Sync>`. P4 transforms (filter / sort / derived column / group-by / aggregate) should register their entry points there — the palette picks them up for free.
2. **`MainThreadDispatcher` is ready for cross-thread post-transform callbacks.** P4 transforms that run on tokio workers (sort over a 100M-row table, aggregate spill) can post Banner-updates + grid re-render closures through the dispatcher. Reference: `crates/dat0-app/src/main_bridge.rs` + UDS-handler call site in `crates/dat0-app/src/window.rs`.
3. **`Banner` shape now carries both primary + secondary action slots.** P4 transform error UX (e.g., "Column type mismatch: rerun with auto-cast?" with primary=AutoCast + secondary=Cancel) should use the new shape directly. Don't re-introduce the string-formatted `push_warning_message` path.
4. **Real Table widget is mounted; `GridDataSource` is its data plumbing.** P4 transforms that emit a new result table can re-bind `WorkspaceShell.data_source` to a new `GridDataSource::for_table(name)` — the LRU cache + Arc-Mutex are already P3a-shipped. The Table widget will re-render via `TableState`.
5. **D-008 cancellation-token trait amendment is still ahead of P4.** P3b's cancel UX uses an ad-hoc `Arc<AtomicBool>` + `engine.interrupt(handle)` (T10). P4 transforms are long-running; D-008's structured `cancel: CancellationToken` parameter on `execute*` would clean up the per-transform cancel ergonomics. Stays P5 per its existing target; surface at P5 entry.
6. **PD-011 / PD-012 cleanup.** PD-011 is a spec-amendment item (spec §3.7 wording vs T9 implementation); PD-012 is a maintainer one-line after the NYC-taxi asset upload. Neither blocks P4 start; both should land before P4 retro for hygiene.
7. **D-014 Memory Budget surface.** If P3c gets split off (or P9c lands first), the slider/number-input + engine reapply path is documented in D-014. Engine work touches `PRAGMA memory_limit` reapply semantics — verify that mid-query reapply is safe before committing to the "live reapply" UX over "applies next window" wording.
