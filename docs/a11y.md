### 1.1 A2 — focus indicators, now measured

A2 was UAT-pending in every prior revision because the ring colour had never
been independently measured, and it changed twice since (A1 collapsed the
two-blues split onto `ring`; UI2 re-derived light's `ring` to `#03459b`). It is
now measured, and the chain is closed end to end:

1. **Every focus ring in the app reads one token.** `Dat0Colors::focus_ring` is
   derived as `self.ring` — `src/theme/tokens.rs:65`. All 16 painted focus rings
   in `src/` read `cx.theme().d0().focus_ring` or receive it as the `ring`
   parameter of `a11y::FocusStopExt::focus_stop` (`src/a11y/mod.rs:43-69`).
   Sites: `settings_ui/panel.rs:131`, `catalog/panel.rs:59,129,175`,
   `overlay.rs:207`, `ai/panel.rs:272`, `view/command_palette.rs:209`,
   `view/export_dialog.rs:219`, `view/activity_rail.rs:78,136`,
   `view/sql_console.rs:663`, `view/saved_query_picker.rs:110`,
   `empty_state.rs:146,325,402`, `grid/mod.rs:589`. There is no seventeenth:
   `grep -rn focus_ring crates/dat0-app/src` returns exactly these plus the
   definition, the doc comments, and the gallery swatch.
2. **The derivation is asserted.** `src/theme/tokens.rs::dat0_colors_derive_from_active_palette`
   (`:369-399`) asserts `dark.d0().focus_ring == dark.ring` and
   `hc.d0().focus_ring == hc.ring`, and asserts the three themes' rings differ.
3. **The ratio is gated above the requirement.** `ring`/`background` sits in
   `NON_TEXT_PAIRS` at **4.5**, not 3.0 (`tests/theme_contrast_gate.rs:86` — the
   doc comment at `:83-84` explains why: `ring` doubles as the single accent).
   Measured by `tests/theme_contrast_gate.rs::non_text_pairs_meet_wcag_1_4_11`:

   | Theme | `ring` | `background` | Measured | WCAG 2.1 AA 1.4.11 requires | Gate enforces |
   |---|---|---|---|---|---|
   | dark | `#58a6ff` | `#101318` | **7.37:1** | 3.0:1 | 4.5:1 |
   | light | `#03459b` | `#fcfcfb` | **8.79:1** | 3.0:1 | 4.5:1 |
   | high-contrast | `#ffff00` | `#000000` | **19.56:1** | 3.0:1 | 4.5:1 |

   The worst case (dark, 7.37:1) clears the A2 requirement by 2.46×.

**A2 = PASS**, evidenced by `tests/theme_contrast_gate.rs::non_text_pairs_meet_wcag_1_4_11`
plus `src/theme/tokens.rs::dat0_colors_derive_from_active_palette`. What is
*not* claimed: the ring's 2 px geometry and its visibility against every
adjacent surface (not just `background`) remain a human check —
`docs/plans/2026-08-08-dat0-production-v1-uat.md` §2 walks it.

## 2. WCAG contrast results

### Method

`crates/dat0-app/tests/theme_contrast_gate.rs` parses each builtin theme JSON,
serialises the parsed `ThemeConfigColors` back to a JSON object so lookups use
the exact serde rename keys (surviving Rust field renames), and calls
`dat0_app::theme::contrast::contrast_ratio` — the WCAG relative-luminance
formula. Tinted (8-digit) tokens go through `composite_over` first, so a
translucent token is measured against what it actually renders as.

Seven test functions, all green:

| Test fn | What it gates |
|---|---|
| `text_pairs_meet_wcag_aa` | 24 text pairs × 3 themes ≥ 4.5:1 (WCAG 1.4.3) |
| `non_text_pairs_meet_wcag_1_4_11` | 10 non-text pairs × 3 themes ≥ 3.0:1 (WCAG 1.4.11), `ring` held at 4.5 |
| `sibling_pairs_all_gated` | Drift alarm: every `X.foreground`/`X.background` family in the JSON must appear in `TEXT_PAIRS` |
| `composited_tints_keep_text_readable` | `selection.background` and `drop_target.background` composited over their real bases, then text-checked |
| `derived_dat0_colors_meet_wcag` | The six derived `Dat0Colors` alpha tints, checked against their real composited values |
| `brand_pairs_meet_wcag` | The UI2 brand sidecar, 6 pairs × 3 themes |
| `brand_fields_all_gated` | Drift alarm: every `Brand` field must be in `BRAND_PAIRS` or in `BRAND_UNGATED` with a stated reason, and a stale `UNGATED` entry fails too |

Reproduce with:

```
cargo test -p dat0-app --test theme_contrast_gate -- --nocapture --test-threads=1
```

### 2.5 Brand sidecar (UI2) — `BRAND_PAIRS`

The brand ships **beside** `ThemeConfig` rather than inside it, because
`ThemeConfig` has no free slot and silently drops unknown keys. It would
therefore have sat entirely outside the gate — and it is the one part of the
palette a marketing page pins by hex, which is exactly the pressure that
produces an inaccessible value. Hence `BRAND_PAIRS`
(`theme_contrast_gate.rs:328-335`) and the `brand_fields_all_gated` drift alarm.

Sidecar values (`src/theme/builtins/*.brand.json`):

| Field | dark | light | high-contrast |
|---|---|---|---|
| `amber` | `#f5a623` | `#985f00` | `#ffff00` |
| `amber_hover` | `#ffb733` | `#8a5600` | `#ffff66` |
| `amber_text` | `#e3a72f` | `#8a3f07` | `#ffff00` |
| `ink_on_brand` | `#101318` | `#ffffff` | `#101318` |
| `ok` | `#3fb950` | `#136229` | `#66ff66` |
| `scan_sweep` | `#f5a62380` | `#985f0080` | `#ffff0000` |

Light's amber is a **dark ochre** taking **white** ink — the inverse of dark and
high-contrast, both of which take near-black ink. Nothing in `src/` may assume a
side: the ink is always read from `brand(cx).ink_on_brand`.

Measured:

| Pair | Threshold | dark | light | high-contrast |
|---|---|---|---|---|
| `ink_on_brand` / `amber` | 4.5 | 9.18 | **5.29** | 17.33 |
| `ink_on_brand` / `amber_hover` | 4.5 | 10.70 | 6.16 | 17.50 |
| `amber_text` / `background` | 4.5 | 8.72 | 7.32 | 19.56 |

checking only `amber` is how a hover state ships unreadable, since the ink never

### 2.6 Exemptions, and why each is not a waiver

| Excluded | Reason | Enforced by |
|---|---|---|
| `border`, `window.border`, `input.border` | WCAG 1.4.11 carves out decorative separators. dat0 uses these exclusively for panel dividers, table hairlines and input outlines, none conveying information independently | `theme_contrast_gate.rs:8-10` |
| `scrollbar.background` | α=0 in dark/light, opaque black in high-contrast; carries no text | `theme_contrast_gate.rs:173-174` |
| `Brand::scan_sweep` | Decorative gradient wash: carries no text, bounds no control, and is switched **fully transparent** in high-contrast (`#ffff0000`), so every pair involving it is 1.00:1 by construction. A threshold would be a lie in one theme regardless of the others | `BRAND_UNGATED` `theme_contrast_gate.rs:346-350`, policed by `brand_fields_all_gated` |

None of these is a relaxation of a failing measurement. The two drift alarms
(`sibling_pairs_all_gated`, `brand_fields_all_gated`) make silent additions to
the exemption set impossible, and `brand_fields_all_gated` also fails on a
**stale** exemption — an excuse outliving the thing it excused.

## 3. Keyboard reachability

### 3.1 Method and status vocabulary

24 integration-test binaries build a real `WorkspaceShell` in a
`VisualTestContext`, force a settled frame, and snapshot the AccessKit tree that
dat0's own render code emits under the test-only `a11y-capture` feature
(`tests/support/mod.rs::A11ySnapshot::capture`, `:102-118`). Content assertions
and geometry stay in lockstep because both key off the same `&'static str`
element id.

**The suites, enumerated by
`grep -l 'A11ySnapshot::capture' crates/dat0-app/tests/*.rs` — 24, not the 10
the master plan estimated:**

`a11y_content.rs`, `a11y_spike.rs`, `ai_nav.rs`, `bottom_dock.rs`,
`catalog_groups.rs`, `catalog_nav.rs`, `chart_uat_window.rs`,
`command_palette_nav.rs`, `crash_report_window.rs`, `dock_chrome_spike.rs`,
`gallery_smoke.rs`, `input_nav.rs`, `keyboard_nav.rs`, `left_dock.rs`,
`modal_b2_nav.rs`, `modal_trap_nav.rs`, `motherduck_window.rs`,
`onboarding_gpui.rs`, `recents_nav.rs`, `right_dock.rs`, `settings_window.rs`,
`sql_console_nav.rs`, `sql_console_transient_nav.rs`, `update_about_window.rs`.

> **Freshness bound.** This inventory is a snapshot of 2026-08-08, taken while

> `keymap.rs` (SH4) both appeared mid-audit and are folded in below;

Run them with:


Status vocabulary — the distinctions matter, and the previous revision collapsed
them:

| Status | Means |
|---|---|
| **keyboard** | A test presses Tab / Shift-Tab / arrows / Enter / Escape through the **real focus chain** and asserts the outcome. This is what A1 actually asks for. |
| **pointer** | A test issues a synthetic click at the element's resolved `debug_bounds` and asserts the outcome. Proves the control is wired and hit-testable; proves **nothing** about keyboard reach. |
| **content** | A test asserts the surface's a11y nodes (labels, roles) are present in the tree. Proves the surface renders; proves nothing about operability. |
| **logic** | A pure unit test over the state machine, no GPUI. |
| **code-verified** | The path exists in source and shares a dispatch path with something tested; not independently exercised. |
| **UAT-pending** | Needs a human. Each such row below carries an explicit reason. |

A "UAT-pending" entry is an honest declaration, not a failure.

## 4. Screen-reader stance

**Accepted out of scope for v1.** This is a substrate fact, not a policy choice.

### Rationale (restating D-015; not reopened)

AccessKit is the bridge that would let a GPUI application expose a platform
accessibility tree to VoiceOver or Orca. dat0 is pinned to `gpui = "=0.2.2"` and
`gpui-component` rev `0f0ab35` (v0.5.1). The P4b T0 probe
(`docs/internal/dat0-p4b-t0-probe.md` §2) verified that AccessKit is **entirely
absent** from both — no dependency, no `AccessibilityNode`, no adapter. A
screen-reader-navigable tree is not exposable on these pins without forking GPUI.

`accesskit` and `accesskit_consumer` (0.21) **do** appear in `Cargo.lock` today,
and that is the one thing about this row that has changed since P4b. They arrive
**only** through the test-only `a11y-capture` cargo feature
(`crates/dat0-app/Cargo.toml:99` — `a11y-capture = ["dep:accesskit", "dep:accesskit_consumer", "gpui/test-support"]`),
enabled via a self-dev-dependency and **off** in `cargo build --release`, where
`.a11y(…)` / `.a11y_label(…)` compile to identity no-ops
(`src/a11y/mod.rs:77-79`, `:246`, `:273`). That is the UAT-automation harness
this whole document leans on — dat0's render code emits an AccessKit
`TreeUpdate` that `kittest` reads inside `cargo test`.

**D-015 stays open.** There is still no OS platform adapter, no always-on
production emission, and no gpui integration, so the running app gains no
screen-reader support. The upside is real but internal: the `.a11y(id, role,
label)` render-site annotations are now dense across the shell, so the day a
GPUI pin ships an adapter, the semantic vocabulary already exists.

One genuine production a11y capability does ship from this module, and it should
not be confused with the test harness: `a11y::FocusStopExt::focus_stop`
(`src/a11y/mod.rs:42-71`) is compiled in release and is what makes an
interactive `div` a real tab stop that takes focus, activates on Enter/Space and
paints a focus ring. It is the mechanism behind almost every **keyboard** row in
§3.

### Spec resolution

Spec §21.2 item A5 (`docs/specs/2026-04-26-dat0-design.md:1207`) reads:

> "Screen-reader compatibility documented (or **accepted out-of-scope for v1
> with rationale in `docs/a11y.md`**)"

This section is that rationale. The resolution is explicitly permitted.

### Tracking

`docs/deferrals.md` **D-015** — "AccessKit / screen-reader selection-tree
exposure", status `open`. Revisit when the GPUI pin advances to a version that
ships an AccessKit adapter. Additional surfaces noted on that entry for whenever
it is picked up: the Connections panel attachment list and the token-prompt
modal, alongside the grid selection/cell semantics tree.

**The v1 a11y baseline is: operability + AA contrast.** Every interactive
element reachable and operable by keyboard (A1), focus rings measurably visible
(A2), and every colour pair — including the brand — meeting WCAG 2.1 AA
(A3/A4).

## 5. Tightest-pair watch

These are the pairs with the least headroom. If any of them is touched, re-run
`cargo test -p dat0-app --test theme_contrast_gate` and update §2 **and** this
table in the same PR. The gate catches the regression automatically; this table
exists so a reviewer knows which edits are dangerous before making them.

|---|---|---|---|---|---|---|
| 1 | `tab.foreground` / `tab.background` | light | **4.56:1** | 4.5 | 0.06 | `light.json` |
| 2 | `info.foreground` / `info.background` | dark | 4.63:1 | 4.5 | 0.13 | `dark.json` |
| 3 | `primary.background` / `background` | dark | 3.70:1 | 3.0 | 0.70 | `dark.json` |

| 6 | `primary.foreground` / `primary.background` | dark | 5.03:1 | 4.5 | 0.53 | `dark.json` |
| 7 | `ink_on_brand` / `amber` | light | 5.29:1 | 4.5 | 0.79 | `light.brand.json` — tightest **brand** pair |
| 8 | `amber` / `background` | light | 5.15:1 | 3.0 | 2.15 | `light.brand.json` |

**Rank 1 is the one to watch.** Light's `tab.foreground` (`#5a636e`) over
`tab.background` (`#dcdfe4`) clears the AA floor by 0.06 — roughly one hex step
on either token. Any future adjustment to the light tab strip must re-run the
gate before it is committed, and must darken `tab.foreground` rather than relax
the threshold.

Never relax a threshold. Never add an exemption to dodge a failing pair. The
precedent (UI-redesign A3) is that the gate drives the final palette values, not
the other way round.
