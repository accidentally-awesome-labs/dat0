## 2. WCAG AA contrast results

### Method

The gate is an automated integration test (`crates/dat0-app/tests/theme_contrast_gate.rs`)
that loads each builtin theme via `Theme::load_builtin(name)`, calls
`dat0_app::theme::contrast::contrast_ratio` (WCAG relative-luminance formula),
and asserts every required pair meets the threshold. The test is run in CI on
every PR via `cargo test -p dat0-app --test theme_contrast_gate`.

### Token matrix

Five token pairs are tested at the 4.5:1 WCAG AA threshold for normal text
(WCAG 2.1 success criterion 1.4.3):

| Token A | Token B | Threshold |
|---------|---------|-----------|
| `foreground` | `background` | 4.5:1 |
| `error` | `background` | 4.5:1 |
| `success` | `background` | 4.5:1 |
| `warning` | `background` | 4.5:1 |
| `accent` | `background` | 4.5:1 |

|-------|-----------|----------------|-----------|--------|
| light | `foreground` / `background` | **15.80:1** | 4.5:1 | PASS |

All 15 pairs pass. Source: `.superpowers/sdd/task-2-report.md` (T2 execution record, P10b).

### `border` exemption

The `border` colour token is **intentionally excluded** from the matrix.
WCAG 2.1 success criterion 1.4.11 (Non-text Contrast) provides a carve-out for
decorative borders and separators whose sole purpose is to visually separate
content regions. dat0's `border` token is used exclusively for panel dividers,
table hairlines, and layout separators — none of them conveying information
independently. The criterion is noted in the gate test doc comment.

### Grid selection — branch A rationale

Grid selected cells use a **translucent tint overlay** (`rgba(0x3b82f622)` /
`rgba(0x3b82f611)` for light/dark) plus a 2 px ring border, not an opaque
accent fill. Cell text colour is unchanged for selected cells — foreground text
still renders on the background colour. Therefore:

- No separate `selection_fg`/`selection_bg` token pair is needed.
- The existing `accent`/`background` pair (≥ 4.5:1 in all themes) subsumes and
  strictly exceeds any WCAG 1.4.11 3.0:1 ring-vs-background requirement.
- No additional pair was added to the gate matrix (branch A decision, P10b T2).

## 3. Keyboard reachability

### Scope and methodology

This table covers every interactive surface in the application. Where keyboard
paths are determinable from code (action registrations in `menu_macos.rs`,
`window.rs`, `grid/keymap.rs`, `view/sql_console.rs`) the row is marked
**code-verified**. Where behaviour depends on GPUI's focus-chain implementation
or widget-level tab-stop wiring that cannot be confirmed without running the
app, the row is marked **UAT-pending** (owed to the T13 manual UAT for P10b).

A "UAT-pending" entry is an honest declaration that the code path exists but
has not been manually exercised in the running app. It is NOT a failure.

## 4. Screen-reader stance

**Accepted out-of-scope for v1.**

### Rationale

AccessKit is the accessibility bridge library that would allow a native desktop
application built on GPUI to expose a platform accessibility tree to screen
readers (VoiceOver on macOS, Orca on Linux). dat0 is pinned to:

- `gpui = "=0.2.2"` (exact version pin in `Cargo.toml`)
- `gpui-component` rev `0f0ab35` (v0.5.1)

A grep of `Cargo.lock` confirms that `accesskit` does not appear at any
transitive depth in the dependency tree — there are 0 occurrences. Neither GPUI
0.2.2 nor gpui-component 0.5.1 ships an AccessKit adapter, and adding one
without forking GPUI is not feasible.

A screen-reader-navigable accessibility tree (selection/cell semantics,
panel roles, live regions) is therefore genuinely out of scope for v1, not a
policy choice — the platform substrate does not exist on the current pins.

### Spec resolution

The master spec §21.2 P10 a11y checklist item A5 reads:

> "Screen-reader compatibility documented (or **accepted out-of-scope for v1
> with rationale in `docs/a11y.md`**)"

This document serves as that rationale. The resolution is explicitly permitted
by the spec.

### Tracking

Deferred as **D-015** ("AccessKit / screen-reader selection-tree exposure") in
`docs/deferrals.md`. Status remains `open`. Target: revisit when the GPUI pin
advances to a version that ships an AccessKit adapter.

The v1 a11y baseline is: **operability + AA contrast** — every interactive
element reachable by keyboard (A1), focus rings visible (A2), token pairs
meeting WCAG 2.1 AA 4.5:1 (A3/A4).

## 5. Tightest pair watch

The tightest-passing contrast pair is **`light: warning / background = 4.87:1`**
(0.37 above the 4.5:1 floor). If the light theme warning colour is ever
adjusted in `crates/dat0-app/src/theme/themes/light.json`, re-run
`cargo test -p dat0-app --test theme_contrast_gate` to confirm it still passes.
The CI gate will catch regressions automatically.
